# GEO 完整投产实现规划

生成时间：2026-07-05

本文是从当前工程状态到完整可投产 GEO SaaS 的总规划。本文不再使用“首发”“MVP”“试点”“原型”作为交付口径；唯一目标是交付一个真实用户可登录、可配置、可采集、可分析、可报告、可复测、可运营、可审计、可维护的生产系统。

对应执行文件：[GEO-Production-v1一次性交付实施计划-2026-07-05.md](GEO-Production-v1一次性交付实施计划-2026-07-05.md)。执行口径为一个 Production v1 版本目标、W1-W10 多工作流并行施工、内部依赖门禁、最终一次总验收和一次正式上线。

## 1. 投产目标

最终系统必须让真实客户和内部交付团队完成完整业务闭环：

```text
租户开通
  -> 用户登录与授权
  -> 创建 GEO 项目
  -> 配置品牌、竞品、市场、平台、Prompt、采集计划
  -> 调用真实外部采集能力
  -> 保存原始证据和审计链
  -> 自动解析回答
  -> 生成可解释评分、信源图谱、竞品对标和风险诊断
  -> 生成客户报告
  -> 生成行动计划
  -> 建立知识库
  -> 生成和审核内容建议
  -> 创建分发任务并回填发布结果
  -> 按观察窗口复测
  -> 输出趋势、预警、复盘和下一轮优化建议
```

投产完成后，fixture/demo 数据只能用于测试和演示环境，不能作为生产功能的默认路径。生产环境所有关键读数必须来自真实项目、真实配置、真实采集、真实证据、真实报告和真实审计事件。

## 2. 当前状态基线

根据归档的 [项目全面复查报告-2026-07-05.md](archive/2026-07-05-old-docs/项目全面复查报告-2026-07-05.md)，当前工程已经具备以下能力：

- Docker 自动端口栈可运行。
- Admin Web、Customer Web、Dashboard Web 和 FastAPI API 可访问。
- 项目创建、项目详情、Prompt 修改、CSV 导入、Customer portal token、报告下载代理已有基础路径。
- fixture runtime E2E 已通过，能够写入 answer runs、report exports、traceability bundles、audit events 和 MinIO artifacts。
- DB/RLS smoke 在指定避让端口后通过。
- 前端 typecheck/build 通过，Python lint/compile 通过。

当前不能投产的关键阻断：

- 真实 OpenAI、Perplexity、Google AI Mode/AIO 采集未打通，当前项目仍是 `fixture` / `not_configured` / `fixture_only`。
- 全量测试仍有 2 个契约测试失败。
- `db-smoke` 默认端口和 observability 默认端口存在冲突风险。
- Customer portal token 通过 URL query 传播，不满足生产安全边界。
- 项目创建和竞品编辑校验不足，已有脏竞品名进入项目数据。
- Dashboard 和部分文档仍混用 GENO/GEO、旧状态和旧入口。
- 完整登录、租户、RBAC、生产部署、安全扫描、备份恢复、告警、变更流程尚未形成投产门禁。
- 知识库、内容工作台、分发任务、预警、复测闭环还没有达到真实业务可用。

## 3. 投产完成定义

只有同时满足以下条件，项目才可以被称为完成：

1. 真实用户可用：客户、运营、分析师、审核人、管理员都能使用自己的账号完成授权范围内的工作。
2. 真实数据可用：项目配置、Prompt、采集结果、评分、报告、行动计划、知识事实、内容、分发、复测都来自真实数据库和对象存储。
3. 真实采集可用：OpenAI、Perplexity、Google、Gemini/Bing/Claude 等配置的平台按项目计划执行，成功率、失败原因、成本和证据可追踪。
4. 证据链完整：任意报告数字都能追溯到 `ReportExport -> VisibilityScoreSnapshot -> ScoreContribution -> AnswerAnalysis -> AnswerRun -> RawAnswer/AnswerCitation/EvidenceAsset -> AuditEvent`。
5. 客户安全可用：客户入口不泄露 token，不暴露内部调试信息，不越权访问其他租户或项目。
6. 内部运营可用：项目、成员、权限、采集任务、人工复核、报告发布、告警、失败重试都有可操作界面。
7. 内容闭环可用：客户资料可导入，知识事实可审核，内容建议可生成、检查、审核、分发、复测。
8. 生产运维可用：部署、迁移、备份、恢复、日志、指标、告警、成本、限流、队列、对象存储都可观测和可演练。
9. 质量门禁可用：所有单元、契约、集成、E2E、安全、权限、迁移、浏览器、性能和恢复测试通过。
10. 文档可交接：用户手册、运营手册、部署手册、故障处理手册、外部 API 申请指南、数据口径说明全部更新。

## 4. 产品入口规划

### 4.1 Admin Web：内部运营与交付后台

Admin Web 是内部团队的唯一操作后台，必须包含：

- 首页：项目总览、待处理事项、失败采集、待审核内容、近期报告、告警。
- 租户管理：创建租户、编辑租户、禁用租户、租户成员、租户级配置。
- 用户与权限：用户邀请、角色分配、项目授权、权限审计、登录历史。
- 项目管理：创建、编辑、归档、恢复、删除项目；项目状态必须中文化且有明确状态机。
- 项目配置：品牌、竞品、市场、语言、城市、行业、官网、别名、禁用口径、客户可见范围。
- 平台配置：OpenAI、Perplexity、Google、Gemini、Bing/Claude 等采集配置、权重、启用状态、限流策略。
- Prompt 管理：列表、搜索、筛选、分页、批量导入、批量编辑、版本、停用、质量检查。
- 采集运行：创建计划、立即运行、暂停、恢复、重试、失败原因、成本、耗时、证据数量。
- 原始证据：回答、引用、截图、HTML、payload hash、collector logs、访问方式、地理、设备、时间。
- 解析复核：自动解析结果、实体确认、品牌/竞品提及、推荐语义、排名、情感、风险、事实准确性。
- 评分配置：公式版本、权重配置、配置文件路径、变更说明、影响范围、历史复算。
- 报告管理：报告生成、预览、审批、导出、发布、撤回、下载、客户可见控制。
- 行动计划：source gap、竞品压制、品牌缺失、错误事实、内容建议、责任人、截止时间、状态。
- 知识库：资料导入、文档解析、事实抽取、事实审核、禁用口径、向量检索状态。
- 内容工作台：内容任务、草稿生成、事实引用、风险检查、人工审核、版本管理。
- 分发任务：目标渠道、负责人、发布时间、发布 URL、状态、失败原因、复测关联。
- 复测与趋势：观察窗口、复测任务、前后对比、趋势归因、报告复盘。
- 系统管理：供应商 key、模型路由、对象存储、队列、任务限流、审计日志、告警配置。

### 4.2 Customer Web：客户门户

Customer Web 是客户可见的单租户/单项目体验，必须包含：

- 安全登录或一次性邀请兑换，不使用 URL query 长期传递 portal token。
- 项目首页：总体分数、趋势、平台表现、竞品态势、风险、行动进度、最新报告。
- AI 可见性：按平台、城市、intent、时间展示 Trigger/Mention/Recommendation、排名、情绪、风险。
- Prompt 明细：客户可见问题、回答摘要、证据入口、引用源、趋势变化。
- 信源图谱：官网、本地媒体、社区、百科、视频、竞品独占信源、source gap。
- 竞品对标：竞品出现率、推荐率、排名、引用重叠、本地相关性、优势/劣势。
- 报告中心：周报、月报、专项报告、PDF/CSV 下载、方法说明、审计摘要。
- 行动计划：客户任务、内部任务、状态、责任人、截止时间、证明材料。
- 内容建议：已审核可见的内容建议、目标页面、证据来源、发布建议。
- 复测结果：7/14/30 天或自定义窗口前后变化，展示趋势而不是单点结论。
- 可解释性：任意指标可点回原始证据和方法说明，但不暴露内部 secret、调试日志、供应商 payload 原文。

### 4.3 Dashboard Web：工程与运营看板

Dashboard Web 不能再作为半成品门面。它必须明确定位：

- 对外不可展示内部工程垃圾信息。
- 对内展示系统健康、任务积压、采集成功率、报告生成成功率、成本、告警、版本、最近部署。
- 如果保留给管理层使用，必须改名为 GEO 运营驾驶舱，数据来自实时 API 或可追溯快照。
- 静态 JSON 只能作为构建时兜底，不能展示过期状态误导用户。

### 4.4 Legacy Web

旧 `apps/web` 只允许作为迁移源或内部临时诊断工具，不作为生产默认入口。所有仍有价值的 `/ops` 能力必须迁移到 Admin Web 或 Dashboard Web；迁移完成后删除旧入口或加严格内网权限。

## 5. 后端与服务规划

### 5.1 API 服务

FastAPI 必须拆成明确业务域，避免继续堆在单一 `main.py`：

- `tenants`：租户、组织、租户配置。
- `auth`：登录、邀请、会话、角色、权限。
- `projects`：项目生命周期、项目配置、状态机。
- `brands`：品牌、品牌别名、官方域名、禁用口径。
- `competitors`：竞品、竞品别名、竞品域名、竞品状态。
- `prompts`：Prompt、intent、导入、版本、质量检查。
- `connectors`：OpenAI、Perplexity、Google、Gemini、Bing/Claude、第三方 SERP。
- `collection_runs`：采集计划、采集运行、失败重试、成本、限流。
- `evidence`：RawAnswer、AnswerCitation、EvidenceAsset、CollectorLog、对象存储代理。
- `analysis`：AnswerAnalysis、实体识别、人工复核、别名确认。
- `scoring`：VisibilityScoreSnapshot、ScoreContribution、公式版本、权重配置。
- `graphs`：Citation Graph、Source Gap、Competitor Benchmark。
- `reports`：ReportExport、报告任务、报告审批、报告下载。
- `actions`：ActionPlan、任务指派、状态流转、复测关联。
- `knowledge`：资料导入、事实抽取、事实审核、向量索引。
- `content`：内容草稿、风险检查、审核流、版本管理。
- `distribution`：发布任务、发布回填、渠道配置。
- `alerts`：告警规则、通知、事件订阅。
- `audit`：AuditEvent、EvidenceLink、访问日志、追溯查询。
- `admin`：系统配置、供应商配置、运维只读诊断。

每个域必须有：

- OpenAPI schema。
- 请求/响应模型。
- 权限检查。
- 审计事件。
- 单元测试和 API 契约测试。
- 数据库事务边界。

### 5.2 Core/Repository

当前 `repository.py` 必须拆分为领域仓储：

- `tenant_repository.py`
- `access_control_repository.py`
- `project_repository.py`
- `prompt_repository.py`
- `connector_repository.py`
- `collection_repository.py`
- `evidence_repository.py`
- `analysis_repository.py`
- `scoring_repository.py`
- `source_graph_repository.py`
- `report_repository.py`
- `action_repository.py`
- `knowledge_repository.py`
- `content_repository.py`
- `distribution_repository.py`
- `audit_repository.py`

拆分原则：

- SQL 与业务状态机分离。
- Repository 不直接拼接不可控字符串。
- 所有写操作必须有审计上下文。
- 所有项目级查询必须接受 actor/project scope。
- 所有跨租户读写必须有显式系统权限。
- 所有 bulk import 必须先整体验证，再事务写入。

### 5.3 Worker 与任务系统

生产系统必须有独立 worker，不允许依赖人工 shell 命令完成主流程：

- collector worker：执行平台采集。
- parser worker：解析回答、实体、引用、情绪、风险。
- scoring worker：计算分数和 ScoreContribution。
- graph worker：构建 Citation Graph 和 Source Gap。
- report worker：生成 PDF/CSV/Markdown 报告。
- knowledge worker：文档解析、事实抽取、向量索引。
- content worker：内容草稿、风险检查、版本生成。
- distribution worker：发布状态同步、失败重试、复测触发。
- notification worker：告警和通知。

任务系统必须支持：

- 定时任务。
- 立即运行。
- 暂停/恢复。
- 失败重试。
- 幂等执行。
- 限流。
- 取消。
- 死信队列。
- 任务可观测。
- 成本统计。

## 8. 分析、评分与图谱规划

### 8.1 Answer Parser

必须支持：

- 文本清洗和结构化。
- 品牌、别名、产品、竞品、实体识别。
- 推荐语义判断。
- 排名位置解析。
- 情感和风险识别。
- 引用源分类。
- 本地相关性判断。
- 事实准确性建议。
- 人工复核覆盖自动结果。

### 8.2 评分引擎

必须支持：

- 公式版本注册。
- 项目级评分配置文件。
- 权重可编辑、可审批、可审计。
- Trigger/Mention/Recommendation 分母分离。
- 平台分、城市分、intent 分、项目总分。
- ScoreContribution 解释包。
- 历史分数按旧公式复算。
- 公式变更影响分析。

评分结果不能只展示总分，必须展示：

- 子指标。
- 分母。
- 权重。
- 样本数。
- 正负证据。
- 局限说明。
- 数据新鲜度。

### 8.3 Citation Graph

必须支持：

- source node 建模。
- source type 分类：官网、媒体、社区、百科、视频、评价站、目录、本地机构、未知。
- source freshness。
- source authority。
- citation overlap。
- 竞品独占源。
- source gap。
- 可点击追溯到 answer runs。
- 图谱导出和报告引用。

### 8.4 Competitor Benchmark

必须支持：

- 3 到 N 个竞品。
- mention rate。
- recommendation rate。
- average position。
- share of voice。
- citation overlap。
- local relevance。
- sentiment/risk。
- topic/intent 分布。
- 竞品优势和品牌缺口。

## 9. 报告、行动计划与复测规划

### 9.1 报告系统

必须支持：

- 周报。
- 月报。
- 基线报告。
- 复测报告。
- 竞品专题报告。
- 信源专题报告。
- 客户可下载 PDF/CSV。
- 内部可下载 evidence appendix。
- 报告审批。
- 报告发布和撤回。
- 不可覆盖版本快照。

每份报告必须包含：

- 方法说明。
- 采样范围。
- 平台和连接器说明。
- 数据时间窗。
- Google/浏览器/人工路径说明。
- 评分公式和版本。
- 审计摘要。
- 分数解释包。
- 原始证据附录。
- 局限和风险说明。

### 9.2 行动计划

必须从证据自动生成行动建议：

- 品牌未出现：补充官网 FAQ、Schema、本地目录、评价源。
- 竞品压制：补充对比页、案例、媒体背书。
- 信息错误：修正官网、FAQ、知识库和第三方页面。
- 信源缺口：新增本地媒体、行业目录、评价平台、权威资料。
- 负面风险：人工处理、客服/PR 跟进、证据记录。
- 内容缺口：生成内容任务并绑定知识事实。

行动计划必须支持：

- 优先级。
- 责任人。
- 截止日期。
- 状态。
- 证据来源。
- 复测窗口。
- 完成证明。
- 客户可见控制。

### 9.3 复测系统

必须支持：

- 自定义观察窗口。
- 7/14/30 天预设窗口。
- 针对行动计划的复测。
- 针对 Prompt/intent/platform/city 的复测。
- 前后窗口差异。
- 统计显著性或置信说明。
- 报告引用。
- 趋势告警。

## 10. 知识库、内容工作台与分发规划

### 10.1 知识库

必须支持：

- 文件上传：PDF、DOCX、TXT、Markdown、CSV。
- URL 导入：官网、FAQ、新闻稿、案例、产品页、帮助中心。
- 文档解析。
- 文本切分。
- 元数据提取。
- 事实抽取。
- 事实状态：draft、approved、deprecated、forbidden。
- 证据来源绑定。
- 人工审核。
- 向量索引。
- 关键词检索。
- 语义检索。
- 禁用口径管理。

### 10.2 内容工作台

必须支持：

- 从 source gap 创建内容任务。
- 从品牌未出现问题创建内容任务。
- 从竞品压制问题创建内容任务。
- 从事实错误创建内容修正任务。
- 内容类型：FAQ、品牌介绍、产品介绍、竞品对比、行业科普、案例稿、新闻稿、社区问答、短视频脚本、白皮书片段。
- RAG 检索 approved 知识事实。
- 草稿生成。
- 事实引用展示。
- 风险检查。
- 人工修改。
- 审核流程。
- 版本管理。
- 多语言支持。

### 10.3 分发任务

必须支持：

- 选择内容版本。
- 选择目标渠道。
- 指派负责人。
- 计划发布时间。
- 发布 URL 回填。
- 发布状态流转。
- 失败原因。
- 发布证明附件。
- 复测任务自动关联。
- 渠道 API 预留。

生产系统不强制所有渠道自动发布，但必须把人工发布回填和复测闭环做完整。

## 11. 权限、安全与合规规划

### 11.1 身份认证

必须完成：

- 用户登录。
- 邀请注册。
- 密码或外部身份提供商。
- MFA 预留。
- session 管理。
- 登录历史。
- 退出登录。
- session 过期。
- 异常登录告警。

### 11.2 RBAC

必须支持角色：

- Super Admin。
- Tenant Admin。
- Project Owner。
- Analyst。
- Knowledge Architect。
- Content Operator。
- Reviewer。
- Client Viewer。

权限必须覆盖：

- 租户级权限。
- 项目级权限。
- 客户只读权限。
- 报告可见权限。
- 内容审核权限。
- 系统配置权限。
- 外部 key 管理权限。
- 审计查询权限。

### 11.3 客户入口安全

必须替换 URL query token：

- 邀请 token 只可兑换一次。
- raw token 只显示一次。
- 数据库存 token hash。
- 兑换后使用 httpOnly secure session cookie。
- token/session 支持 TTL。
- 支持撤销和轮换。
- Referer policy 防泄露。
- 访问日志脱敏。
- 下载报告走权限校验和短期签名 URL。

### 11.4 合规边界

必须保证：

- 不绕过平台安全机制。
- 不使用违规账号池。
- 采集频率可控。
- 采集方法可披露。
- 内容不生成虚假资质、虚假案例、虚假排名。
- 对医疗、金融、教育等敏感行业启用二次审核。
- 对外内容保留证据来源和审核记录。

## 14. Production v1 工作流映射

本总规划不再使用 A-G 工作包作为施工顺序。所有能力都纳入同一个 GEO Production v1 scope，执行以 [GEO-Production-v1一次性交付实施计划-2026-07-05.md](GEO-Production-v1一次性交付实施计划-2026-07-05.md) 的 W1-W10 工作流为准。

| 工作流 | 能力归属 | 主要目标 |
| --- | --- | --- |
| W1 架构与工程基线 | 当前阻断清零、FastAPI 边界、Repository 拆分、测试修复、demo fallback 清理 | 工程基线可信，后续模块不在不稳定基础上返工 |
| W2 Auth / Tenant / RBAC / RLS | 用户、租户、成员、邀请、session、角色、权限、RLS | 系统具备真实多用户 SaaS 边界 |
| W3 Connector / Collection | OpenAI、Perplexity、Google manual、Google browser/SERP、调度、成本、失败分类 | 真实外部采集可运行、可重试、可计费 |
| W4 Evidence / Audit | RawAnswer、Citation、EvidenceAsset、AuditEvent、Traceability Bundle | 任意报告数字可追溯到原始证据 |
| W5 Analysis / Scoring | Answer Parser、人工复核、ScoreContribution、Citation Graph、Source Gap、Competitor Benchmark | 真实采集可转成可解释业务结论 |
| W6 Report / Customer Portal | ReportExport、PDF/CSV/Markdown、审批、发布、撤回、客户安全查看 | 客户可安全接收正式报告 |
| W7 Action / Retest | 行动计划、任务流转、复测、趋势、告警 | 从报告进入持续优化 |
| W8 Knowledge / Content / Distribution | 知识库、内容工作台、审核、分发回填、分发后复测 | 补齐完整 GEO 服务闭环 |

知识库、内容生成、分发自动化可以并行做基础设施和 UI，但不得绕过真实采集、证据链、评分、报告闭环独立投产。

## 16. 不允许上线的情况

出现以下任一情况，不允许投产：

- 生产环境仍默认使用 fixture 数据。
- OpenAI/Perplexity/Google 任一被声明支持的平台没有真实采集验收。
- 报告数字不能追溯到原始证据。
- 客户 token 出现在 URL query、普通日志或 Referer 中。
- 客户可越权访问其他项目。
- RLS smoke 或权限测试失败。
- 采集失败没有明确失败原因。
- provider key 明文入库或入日志。
- 新建真实项目仍可能写入 demo fallback 数据。
- 报告可被覆盖导致历史不可复盘。
- 未审核事实可进入正式内容。
- 未审核内容可进入分发任务。
- 全量测试、迁移测试、安全扫描或生产部署演练失败。

## 17. 执行方式

Production v1 不按“先做小版、再逐步扩”的方式推进。正确执行方式是一个版本目标、多条工作流并行、强依赖先行、统一最终验收。

并行启动原则：

1. W1、W2、W3、W4、W9、W10 从第一天启动。
2. W5 在 W3/W4 的数据契约冻结后进入核心实现。
3. W6 在 W2/W5 的权限和评分契约冻结后进入核心实现。
4. W7 在 W5/W6 的报告和评分链路可用后进入核心实现。
5. W8 的基础表、对象存储导入、UI shell 可以提前做；知识事实、内容建议、分发回填必须和真实报告、行动计划、复测闭环打通后才算完成。

每个工作流都必须以可运行代码、可访问界面、可复现测试、可审计数据和更新后的文档作为交付物。单纯写计划、写静态页面、写 fixture、写无法连接真实服务的接口，都不能算完成。

## 18. 下一步立即动作

下一轮实现直接按 Production v1 第一批强依赖 backlog 并行启动：

1. W1：修复全量测试失败、本地端口门禁、Dashboard/GEO 口径、项目与竞品校验、KoalaHome 脏数据、真实项目创建 fallback。

3. W3：完成 Connector SDK spike，确认 OpenAI、Perplexity、Google 返回结构、成本字段、citation 形态和失败分类。
4. W4：冻结 RawAnswer / Citation / EvidenceAsset / AuditEvent / EvidenceLink 契约和对象存储访问策略。
5. W9：补齐 Prometheus/Grafana/OpenTelemetry/Sentry/备份恢复/secret 管理的最小生产运行门禁。

这些动作不是阶段一，也不是可对外发布的小版本；它们只是 GEO Production v1 中最先解除依赖风险的施工入口。
