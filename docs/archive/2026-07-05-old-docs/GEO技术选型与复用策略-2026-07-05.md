本文回答一个工程原则问题：哪些能力用成熟组件，哪些能力必须自研。结论很明确：GEO 项目不应该从头实现身份认证、对象存储、队列、监控、向量检索、图存储、LLM 网关、浏览器自动化、文档解析、邮件发送、PDF 生成等通用基础设施；应该自研的是 GEO 的业务数据契约、证据链、采集归一化、评分解释、报告口径、客户/运营工作流和可追溯审计。

## 1. 总原则

1. 优先复用成熟、可自托管、社区活跃、接口清晰的组件。
2. 对外部组件加适配层，不让业务代码直接绑定某个供应商或库。
3. 自研只放在 GEO 差异化核心：采集证据契约、解析归一化、评分解释、信源图谱、竞品对标、报告追溯、行动计划和复测闭环。
4. 生产安全能力不手写简化版本，优先接入成熟身份、session、secret、审计、备份和监控方案。
5. 当前仓库已有的 FastAPI、Next.js、PostgreSQL+pgvector、MinIO、Playwright、LiteLLM、Prometheus/Grafana 继续沿用，除非有明确性能、合规或维护瓶颈。

## 3. Build vs Buy 矩阵

### 3.1 身份认证与权限

| 能力 | 选型 | 不从头实现的部分 | 自研部分 |
| --- | --- | --- | --- |
| 登录/SSO/OIDC | Keycloak 或托管 OIDC provider | 密码、MFA、OIDC、session policy、账号安全 | GEO tenant/project role 映射、项目级权限矩阵 |
| Session | OIDC session + 后端 session 表 | token 签发、过期、刷新、撤销基础机制 | portal invitation 兑换、项目 scope、访问审计 |
| RBAC | 后端自研权限矩阵 + 数据库 RLS | 不写通用 IAM 平台 | GEO 角色、资源、动作、租户/项目 scope |

推荐：生产优先 Keycloak/OIDC；如果短期不接 Keycloak，也必须把 auth 抽象成 provider interface，避免后续重写全部 API。

### 3.2 数据库、搜索、向量与图

| 能力 | 选型 | 不从头实现的部分 | 自研部分 |
| --- | --- | --- | --- |
| 主业务库 | PostgreSQL | 事务、索引、约束、RLS、JSONB、全文搜索 | GEO schema、审计关系、状态机 |
| 向量检索 | pgvector 起步，规模后 Qdrant/Milvus | ANN 索引、相似度检索 | 文档 chunk、metadata、知识事实绑定 |
| 搜索 | PostgreSQL full-text 起步，后续 OpenSearch | 文本索引、复杂搜索、日志搜索 | GEO 搜索字段、权限过滤 |
| 图谱 | PostgreSQL 邻接表起步，复杂后 Neo4j | 图遍历、图查询、可视化生态 | Citation Graph 数据契约、source gap 规则 |

推荐：现在不用立刻引入 Qdrant/Milvus/Neo4j/OpenSearch。先用 PostgreSQL 覆盖生产早期规模，但接口按可替换设计。

### 3.3 对象存储与文件处理

| 能力 | 选型 | 不从头实现的部分 | 自研部分 |
| --- | --- | --- | --- |
| 对象存储 | MinIO/S3 | 文件存储、bucket policy、presigned URL | EvidenceAsset 元数据、权限代理、hash 校验 |
| PDF/DOCX/HTML 解析 | unstructured / Apache Tika / PyMuPDF 等 | 文档解析、格式抽取 | 知识事实 schema、审核流、证据绑定 |
| 报告 PDF | Playwright/Puppeteer HTML print 或 WeasyPrint | PDF 渲染 | 报告模板、方法说明、追溯附录 |
| CSV/XLSX | Python csv/openpyxl | 格式读写 | 行级校验、导入批次、审计 |

推荐：对象存储继续 MinIO/S3 兼容；文档解析不要手写，优先接成熟解析库，业务层只管事实抽取和审核。

### 3.4 任务队列与调度

| 能力 | 选型 | 不从头实现的部分 | 自研部分 |
| --- | --- | --- | --- |
| 短任务队列 | Celery/RQ/Dramatiq + Redis/Valkey | 入队、重试、并发、worker 管理 | GEO 任务类型、幂等 key、审计 |
| 长流程编排 | Temporal | durable workflow、重试、状态恢复 | 采集-解析-评分-报告 workflow 定义 |
| 定时任务 | Temporal schedule / cron / scheduler service | 时间调度 | 项目采集计划语义 |

推荐路线：短期先把现有 Python worker 标准化成统一 task interface；生产化时优先引入 Temporal 处理采集、报告、复测这类长流程。Redis 许可证有变化，若追求严格开源，缓存/队列优先 Valkey。

### 3.5 LLM、采集与外部平台

| 能力 | 选型 | 不从头实现的部分 | 自研部分 |
| --- | --- | --- | --- |
| LLM 网关 | LiteLLM | 多模型路由、统一调用、基础重试 | GEO prompt version、成本归因、审计 |
| OpenAI | 官方 API + connector adapter | 模型推理、搜索能力、SDK/HTTP 调用 | answer/citation 归一化、证据归档 |
| Perplexity | 官方 API + connector adapter | 搜索回答、引用返回 | answer/citation 归一化、成本和失败分类 |
| Google | Playwright + SERP provider + manual backfill | 浏览器自动化、第三方 SERP 能力 | 触发状态、地理/设备/账号状态、方法披露 |
| 浏览器采集 | Playwright | 浏览器控制、截图、HTML | selector 配置、失败分类、证据绑定 |

推荐：connector adapter 自研，provider 调用不自研。所有 provider 走统一 `CollectorBackend` 和 `LLMGateway` 接口。

### 3.6 前端与 UI

| 能力 | 选型 | 不从头实现的部分 | 自研部分 |
| --- | --- | --- | --- |
| 前端框架 | Next.js + React + TypeScript | SSR/路由/server actions/build | GEO 页面和交互 |
| UI 组件 | 优先引入成熟组件库，如 shadcn/ui/Radix primitives | 基础弹窗、tabs、accordion、dropdown、table primitives | 项目详情、证据图谱、评分解释业务组件 |
| 表单 | React Hook Form + Zod 或等价 | 表单状态、schema 校验 | GEO 表单字段、业务规则 |
| 表格 | TanStack Table 或等价 | 排序、筛选、分页、列控制 | Prompt/evidence/report/action 表格配置 |
| 图表 | ECharts/Recharts/Nivo 选一 | 折线、柱状、饼图、tooltip | GEO 指标口径和 drill-down |
| 图谱可视化 | React Flow / Cytoscape.js / D3 选一 | 节点边布局、交互 | Citation Graph 数据映射、权限脱敏 |

推荐：当前前端依赖很轻，后续不要手写复杂 table、dialog、form、graph primitives。优先引入成熟 UI 基础库，但保持视觉和业务组件自控。

### 3.7 监控、日志、错误追踪

| 能力 | 选型 | 不从头实现的部分 | 自研部分 |
| --- | --- | --- | --- |
| 指标 | Prometheus | 指标采集和查询 | GEO 业务指标定义 |
| 可视化 | Grafana | dashboard、alert panel | GEO dashboard 配置 |
| tracing | OpenTelemetry | trace/span 标准 | request/collection/report span 命名 |
| 错误追踪 | Sentry 或同类 | error grouping、release tracking | project/tenant tags、PII 脱敏 |
| LLM observability | Langfuse / promptfoo | LLM trace/eval | GEO parser/evaluator 样本集 |

推荐：当前已有 Prometheus/Grafana。下一步优先加 OpenTelemetry/Sentry，而不是自研错误追踪平台。

### 3.8 通知与邮件

| 能力 | 选型 | 不从头实现的部分 | 自研部分 |
| --- | --- | --- | --- |
| 邮件发送 | Resend/SendGrid/AWS SES/SMTP adapter | 邮件投递、退信、模板变量基础 | GEO 邀请、报告发布、告警语义 |
| 应用内通知 | 自研轻量表 + worker | 不需要买复杂系统 | notification type、read state、project scope |
| 告警通知 | Grafana Alerting 或自研 alert worker 接 webhook | 告警路由 | GEO 阈值、责任人、升级策略 |

推荐：邮件投递不要自研；只自研通知业务对象和权限。

### 3.9 支付与商业化

当前完整投产计划未覆盖收费。如果要商业化订阅，不建议自研支付：

- 订阅/账单：Stripe Billing 或同类。
- 发票/税务：依赖支付服务商。
- 自研部分：套餐、用量、项目额度、采集预算、权限映射。

如果近期没有收费上线需求，可暂不实现，但成本模型必须先做。

## 4. 必须自研的 GEO 核心

以下能力不应该外包给通用 SaaS，也不能只用现成组件拼起来：

1. 项目级 GEO 数据模型：品牌、竞品、Prompt、市场、平台、采样窗口。
2. 采集归一化：不同平台回答、引用、截图、HTML、payload 统一为 AnswerRun/RawAnswer/AnswerCitation/EvidenceAsset。
3. 触发状态模型：`surface_triggered` 与 `answer_present` 不能混淆。
4. 证据链：ReportExport 到原始证据的可追溯链。
5. 评分公式和解释包：VisibilityScoreSnapshot、ScoreContribution、公式版本和历史复算。
6. Citation Graph 和 Source Gap 的业务口径。
7. Competitor Benchmark 的 GEO 指标口径。
8. 行动计划生成规则：从证据缺口到可执行任务。
9. 复测闭环：观察窗口、前后对比、趋势和局限说明。
10. 客户门户的可见范围和脱敏口径。
11. 审计事件语义：采集、解析、人工复核、报告、发布、客户访问。

这些是产品护城河，必须由本项目控制。

## 5. 不应该自研的能力

明确不要从零实现：

- 密码系统、MFA、OIDC。
- 通用对象存储。
- 通用队列和 durable workflow。
- 通用向量数据库。
- 通用图数据库。
- 通用搜索引擎。
- 通用 LLM 网关。
- 通用浏览器自动化。
- 通用 PDF 渲染器。
- 通用文档解析器。
- 通用图表/表格/弹窗组件。
- 通用邮件发送。
- 通用监控、日志聚合、错误追踪。
- 通用支付/订阅。

项目可以写 adapter、schema、权限和审计，但不应该重写这些基础产品。

## 6. 推荐目标架构

### 6.1 近期生产化架构

```text
Next.js Admin / Customer / Dashboard
  -> FastAPI domain routes
  -> PostgreSQL + pgvector
  -> MinIO/S3
  -> Python workers
  -> LiteLLM
  -> Playwright
  -> Prometheus/Grafana
  -> OIDC/Keycloak
```

近期不强制引入 Neo4j、Qdrant、OpenSearch、Temporal，但接口和数据模型必须允许后续替换。

### 6.2 中期扩展架构

触发条件满足后再引入：

| 组件 | 触发条件 |
| --- | --- |
| Temporal | 采集/报告/复测流程需要跨小时、可恢复、可人工介入 |
| Qdrant/Milvus | pgvector 查询性能或过滤能力不足 |
| Neo4j | Citation Graph 查询超过 PostgreSQL 邻接表能力 |
| OpenSearch | Prompt/evidence/report 搜索和日志检索复杂度上升 |
| ClickHouse | 业务事件和成本分析量超过 PostgreSQL 分析承载 |
| Langfuse | LLM parser/evaluator 需要系统化评测和追踪 |
| Sentry | 进入真实客户环境前必须接入 |

## 7. Production v1 工作流需要落实的地方

`GEO-Production-v1一次性交付实施计划-2026-07-05.md` 中以下工作流必须在执行时落实为“选型 + adapter + 集成”，而不是“从头实现”：

- W2 身份认证：优先 OIDC/Keycloak，不手写密码和 MFA。
- W3 connector：provider 调用用官方 API/SDK/HTTP，项目只写 adapter。
- W3/W9 调度和长流程：先标准化 worker interface，生产长流程优先 Temporal。
- W6 报告 PDF：使用 HTML-to-PDF 渲染器，不自研 PDF layout engine。
- W8 知识库解析：使用 unstructured/Tika/PyMuPDF 等，不手写解析器。
- W8 向量检索：先 pgvector，规模后换 Qdrant/Milvus。
- W9 监控告警：复用 Prometheus/Grafana/OpenTelemetry/Sentry。
- 前端复杂表格/表单/图谱：引入成熟组件库。

## 8. 已接受的技术决策

以下 ADR 已固化为当前执行口径：

1. [ADR 0002](../decisions/0002-auth-provider-and-rbac.md)：身份认证采用 OIDC-compatible 边界，生产优先 Keycloak 或托管 OIDC provider；GEO 自研 tenant/project RBAC 和审计语义。
2. [ADR 0003](../decisions/0003-task-queue-and-workflow.md)：短期标准化现有 Python worker；长流程生产化优先 Temporal；必要短队列可用 Celery/RQ/Dramatiq + Valkey。
3. [ADR 0004](../decisions/0004-object-storage-and-evidence-assets.md)：对象存储统一 S3-compatible；dev/staging 默认 MinIO，production 可替换 S3/R2/MinIO。
4. [ADR 0005](../decisions/0005-observability-error-tracking-and-alerting.md)：指标 Prometheus、看板 Grafana、追踪 OpenTelemetry、错误追踪 Sentry 或同类。
5. [ADR 0006](../decisions/0006-vector-search-and-text-search.md)：向量和文本搜索先用 PostgreSQL + pgvector/full-text，规模不足时迁移 Qdrant/Milvus/OpenSearch。
6. [ADR 0007](../decisions/0007-graph-store-for-citation-graph.md)：Citation Graph 先用 PostgreSQL 邻接表，复杂图查询再迁移 Neo4j/Jena。
7. [ADR 0008](../decisions/0008-document-parsing-and-knowledge-extraction.md)：文档解析不自研，使用 unstructured/Tika/PyMuPDF/docling 等 parser adapter。
8. [ADR 0009](../decisions/0009-report-rendering-and-email-delivery.md)：报告 HTML 由 GEO 生成，PDF 起步用 Playwright HTML print；邮件用 SMTP/SES/SendGrid/Resend adapter。
9. [ADR 0010](../decisions/0010-frontend-component-stack.md)：前端继续 Next.js/React/TypeScript，引入 shadcn/Radix、Zod/React Hook Form、TanStack Table，并在图表/图谱任务中选择 ECharts/Recharts、React Flow/Cytoscape。

仍需后续补充的决策：

- Connector 统一接口和供应商适配策略。
- 证据链和报告追溯数据契约。
- Google SERP provider 具体供应商、成本、合规和方法披露。
- Secret 管理：本地 env/Docker secret 到生产 Vault/云 secret manager 的落地路径。

## 10. 执行约束

- 新增基础能力前，先查是否已有成熟组件。
- 引入组件前，必须写 adapter 边界，不能让业务逻辑直接散落调用第三方 SDK。
- 任何 provider key、session、token、raw credential 不允许明文入库、入日志、入报告。
- 任何生产路径不能依赖 fixture mode。
- 任何复杂 UI 控件不要手写低层交互，优先成熟组件。
- 任何长期任务不要只靠同步 HTTP request。
- 任何可复用基础设施不要放进 `main.py` 或巨型 repository。
