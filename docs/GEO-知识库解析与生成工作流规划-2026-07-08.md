## 1. 总目标

本规划定义 GEO Production v1 中知识库从“导入资料”到“生成 Prompt 和 GEO 文案”的完整生产工作流。

最终用户必须能够：

1. 在项目详情页导入本地文件、URL、站点、文本和 CSV。
2. 使用成熟开源组件完成文件解析、OCR、表格抽取、网页抓取、清洗、切分和向量索引。
3. 在前端看到每个文件、网页、chunk、表格、事实和生成结果的状态。
4. 人工审核品牌事实、竞品事实、市场事实和信源事实。
5. 只用已批准事实生成 Prompt 候选、FAQ、GEO 文案和内容草稿。
6. 从任何 Prompt 或文案追溯到事实、chunk、解析块、原始文件或网页证据。
7. 对导入质量、解析质量、chunk 质量、事实质量、生成质量做统一质检。

本项目不自研以下能力：

- PDF 版面理解；
- OCR；
- 表格结构抽取；
- 文档 partition；
- chunk 算法底层实现；
- 站点爬虫核心；
- 向量数据库；
- embedding 模型训练。

我们只实现：

- GEO 业务契约；
- adapter 编排；
- 前端流程；
- 状态机；
- 审核门禁；
- 证据链；
- 质量检查；
- 测试验收。

本规划采用**生产编排式规划**，不再把知识库能力写成松散功能清单。所有实现都必须明确：

- 谁是总任务；
- 谁是子任务；
- 哪些状态属于执行状态；
- 哪些状态属于审核状态；
- 哪些状态可重试；
- 哪些结果是派生产物；
- 哪些质量门禁会阻断后续流程；
- 哪些失败允许 partial success；
- 哪些产物必须可追溯到原始文件或网页。

## 2. 技术选型

### 2.1 总体架构

采用 **Adapter 编排架构**。

```text
Admin Web
  -> API
  -> Pipeline Run
  -> Pipeline Stages
  -> Import / Crawl / Parse / Chunk / Embedding / Extraction / Generation Jobs
  -> Workers
  -> Open-source adapters
  -> Object Store / Postgres / Qdrant
  -> Human Review
  -> Traceability / Quality Gates
```

关键决策：

| 类别 | 决策 | 用途 |
| --- | --- | --- |
| 文件上传 UI | Uppy Dashboard 风格 | 拖拽上传、队列、进度、失败重试 |
| 站点爬取 | Crawl4AI | URL、站点、JS 渲染、Markdown、截图证据 |
| 主解析引擎 | Docling | PDF、Office、HTML、图片、表格、版面理解 |
| 复杂中文/扫描件 | MinerU | 扫描 PDF、复杂表格、公式、中文版面 |
| 通用 partition | Unstructured | 标题、段落、列表、表格、元素拆分 |
| 清洗/切分参考 | Haystack | DocumentCleaner、DocumentSplitter |
| 兜底文本抽取 | Apache Tika | 未知格式、元数据和纯文本兜底 |
| 轻量 Markdown | MarkItDown | 快速转 Markdown |
| 向量数据库 | Qdrant | chunk embedding 检索和 payload filter |
| Embedding | BGE-M3 | 本地多语言 embedding |
| 生成模型 | DeepSeek v4 flash | 事实抽取、Prompt 候选、GEO 文案 |
| 对象存储 | MinIO / S3-compatible | 原始文件、网页、截图、解析产物、表格产物 |

## 3. 生产编排模型

### 3.1 总任务：`knowledge_pipeline_runs`

`knowledge_pipeline_runs` 表示一次完整 GEO 知识库生产流水线。它不是单纯导入任务，也不承载每个阶段的细节状态。

一个 pipeline run 可以覆盖：

```text
import jobs
-> crawl jobs
-> parser runs
-> chunk jobs
-> embedding jobs
-> fact extraction jobs
-> prompt generation jobs
-> content generation jobs
-> quality gate runs
```

关键字段：

- `id`
- `project_id`
- `run_type`：full_ingestion / reparse / rechunk / reindex / fact_refresh / prompt_generation / content_generation / full_rebuild
- `status`
- `entry_source`：file / url / site / text / csv / mixed
- `market_code`
- `locale`
- `city`
- `created_by`
- `started_at`
- `completed_at`
- `failed_step`
- `blocking_quality_gate`
- `waiting_review_stage_key`：fact_review / prompt_review / content_review / publish_or_export
- `waiting_review_count`
- `summary`
- `metadata`

总链路：

```text
pipeline_run
-> import_job
-> source_assets
-> crawl_jobs
-> parser_runs
-> blocks / tables / ocr_spans / page_snapshots
-> chunk_jobs
-> chunks
-> embedding_jobs
-> qdrant points
-> fact_extraction_jobs
-> fact_candidates
-> review gates
-> prompt_generation_jobs
-> prompt_candidates
-> content_generation_jobs
-> content_drafts
-> knowledge_trace_refs
```

### 3.2 总任务状态：`knowledge_pipeline_runs.status`

`pipeline_run.status` 只表达整条流水线的总体状态，不表达 `parsed`、`chunked`、`indexed`、`fact_candidates_ready` 这类阶段产物状态。

状态：

```text
draft
ready
queued
running
waiting_human_review
succeeded
partial_succeeded
failed
cancelled
```

| 状态 | 含义 |
| --- | --- |
| `draft` | 任务已创建，但来源或配置未完整 |
| `ready` | 来源、策略、权限、配额、预检查均通过，可启动 |
| `queued` | 已入队等待 worker |
| `running` | 任一子任务正在执行 |
| `waiting_human_review` | 自动处理完成，等待事实、Prompt 或文案审核 |
| `succeeded` | 所有必需子任务和质量门禁通过 |
| `partial_succeeded` | 部分来源失败，但可用产物已生成 |
| `failed` | 阻断性失败，无法形成可用知识库产物 |
| `cancelled` | 用户或系统取消 |

当 `pipeline_run.status=waiting_human_review` 时，必须通过 `waiting_review_stage_key` 和 `waiting_review_count` 指明具体阻塞点，例如：

```json
{
  "waiting_review_stage_key": "fact_review",
  "waiting_review_count": 37
}
```

前端不得只显示“等待人工审核”，必须显示“等待事实审核：37 条”这类可操作信息。

### 3.3 阶段状态：`knowledge_pipeline_stages`

新增阶段表：

```text
knowledge_pipeline_stages
```

关键字段：

- `id`
- `pipeline_run_id`
- `project_id`
- `stage_key`
- `status`
- `required`
- `blocking`
- `started_at`
- `completed_at`
- `retry_count`
- `error_code`
- `error_message`
- `summary`
- `metadata`

固定 `stage_key`：

```text
source_precheck
asset_ingestion
crawl
parse
ocr
table_extract
chunk
quality_summary
embedding
fact_extract
fact_review
prompt_generate
prompt_review
content_generate
content_review
trace_verify
publish_or_export
```

阶段执行状态：

```text
not_started
queued
running
succeeded
skipped
failed
retrying
blocked
waiting_review
```

示例：

```text
pipeline_run.status = running

source_precheck = succeeded
asset_ingestion = succeeded
crawl = succeeded
parse = running
ocr = not_started
table_extract = not_started
chunk = not_started
embedding = not_started
fact_extract = not_started
```

`ocr` 和 `table_extract` 是 parser run 的派生虚拟阶段，首版不单独创建 `ocr_jobs` 或 `table_extract_jobs`。Parser Worker 在同一个 `knowledge_parser_runs` 内完成 OCR 和表格抽取，并写入 `knowledge_ocr_spans`、`knowledge_tables` 和对应 quality findings；这两个 stage 只用于前端展示进度、skipped / succeeded / blocked 状态和质量结果。

`quality_summary` 不执行具体检查，只汇总所有 `knowledge_quality_gate_runs` 和 `knowledge_quality_findings`。具体检查由各 stage 对应的 quality gate 执行，例如 parse 阶段运行 `parser_quality_gate`，chunk 阶段运行 `chunk_quality_gate`。

### 3.4 子任务状态

#### `knowledge_import_jobs.status`

只表示来源导入任务，不表示解析、chunk、index 或事实生成。

```text
draft
ready
queued
running
succeeded
partial_succeeded
failed
cancelled
```

#### `knowledge_source_assets.status`

表示单个文件或网页资产状态。

```text
registered
uploaded
prechecked
accepted
rejected
processing
processed
failed
disabled
archived
```

#### `knowledge_parser_runs.status`

表示解析运行。

```text
queued
running
succeeded
fallback_succeeded
failed
cancelled
```

`fallback_succeeded` 必须保留，因为前端需要明确展示：

```text
指定引擎失败，已使用 fallback 引擎完成解析
```

#### `knowledge_chunks.status`

chunk 是知识单元，不是任务。

```text
active
disabled
archived
superseded
```

chunk embedding 独立状态：

```text
pending
embedded
failed
disabled
stale
```

#### `knowledge_fact_candidates.status`

事实候选使用审核状态。

```text
pending_review
approved
rejected
archived
forbidden
superseded
merged
needs_reextract
```

| 状态 | 含义 |
| --- | --- |
| `pending_review` | 待人工审核，不得进入生成 |
| `approved` | 已批准，可同步到 approved fact 并进入生成 |
| `rejected` | 已拒绝，不得进入生成 |
| `archived` | 已归档，不进入默认列表和生成上下文 |
| `forbidden` | 明确禁用，后续重抽取也不得自动恢复 |
| `superseded` | 被更新事实替代 |
| `merged` | 已合并到已有 approved fact |
| `needs_reextract` | 审核人要求重新抽取，不可进入生成 |

#### `prompt_candidates.status`

```text
pending_review
approved
rejected
edited_approved
imported
archived
superseded
```

#### `content_drafts.status`

```text
pending_human_review
approved
rejected
needs_revision
published
exported
archived
```

`approved` 只表示文案审核通过，`published` 和 `exported` 才表示对外使用动作。发布、导出都必须独立写审计事件。

### 3.5 可重试与 partial success 规则

可重试对象：

- `knowledge_pipeline_stages`
- `knowledge_import_jobs`
- `crawl_jobs`
- `knowledge_parser_runs`
- `chunk_jobs`
- `embedding_jobs`
- `fact_extraction_jobs`
- `prompt_generation_jobs`
- `content_generation_jobs`
- `quality_gate_runs`

不可通过重试直接改变的对象：

- `knowledge_chunks.status`
- `knowledge_fact_candidates.status`
- `prompt_candidates.status`
- `content_drafts.status`

这些对象属于产物或审核状态，只能通过审核、禁用、归档、重解析或重生成改变。

允许 `partial_succeeded` 的场景：

1. 多文件导入中部分文件失败，但至少一个文件完成 parse/chunk/index。
2. 站点爬取中部分 URL 失败，但达到最低有效页面数。
3. 表格抽取失败，但正文 blocks 可用，且 parser quality gate 未阻断。
4. embedding 部分失败，但 active chunk 的 embedding 成功率达到门槛。
5. fact extraction 部分失败，但有足够 approved candidates 进入审核。

不允许 `partial_succeeded` 的场景：

1. 所有来源都失败。
2. 无任何 active chunk。
3. traceability gate 失败。
4. security gate blocked。
5. 所有事实都无证据。

量化阈值：

| 配置项 | 默认值 | 用途 |
| --- | --- | --- |
| `crawl_min_success_pages` | 1 | 站点爬取至少成功页面数 |
| `crawl_min_success_ratio` | 0.3 | 站点爬取最低成功率 |
| `parse_min_success_assets` | 1 | 多来源导入至少成功解析资产数 |
| `chunk_min_active_chunks` | 1 | 至少生成 active chunk 数 |
| `embedding_min_success_ratio` | 0.8 | active chunk embedding 最低成功率 |
| `fact_min_candidate_count` | 1 | 至少生成有证据 fact candidate 数 |
| `trace_required_for_generated_outputs` | true | Prompt 和文案生成结果必须有 trace |
| `security_block_always_fails` | true | security gate 阻断时 pipeline 不得 partial success |

`partial_succeeded` 判定规则：

| 场景 | partial success 条件 |
| --- | --- |
| 多文件导入 | 至少 1 个 source asset 完成 parse / chunk / index |
| 站点爬取 | 成功页面数 >= 1 且成功率 >= 30% |
| embedding | active chunks embedding 成功率 >= 80% |
| fact extraction | 至少生成 1 条带 `source_chunk_ids` 的 fact candidate |
| generation | 每个 candidate / draft 必须有 `source_fact_ids` 和 `source_chunk_ids` |

### 3.6 状态与版本一致性规则

1. `pipeline_run.status` 只表达总任务状态，不表达阶段产物状态。
2. `pipeline_stage.status` 只表达阶段执行状态，不表达审核决策。
3. job status 只表达异步任务执行状态。
4. chunk / fact_candidate / prompt_candidate / content_draft status 表达产物生命周期或审核状态。
5. 审核状态不得通过 retry 直接改变。
6. 所有可重跑产物必须记录生成它的 job id、pipeline_run_id 和版本信息。
7. 当 parser、chunk profile、embedding model、fact extraction prompt、generation template 或 quality gate config 变化时，新产物不得静默覆盖旧产物，旧产物必须标记 stale、superseded 或 archived。

### 3.7 重跑与版本化规则

所有可重跑链路必须记录以下版本字段：

- `parser_adapter_version`
- `parser_engine_version`
- `chunk_profile_version`
- `cleaner_profile_version`
- `embedding_model_version`
- `fact_extraction_prompt_version`
- `prompt_generation_template_version`
- `content_generation_template_version`
- `quality_gate_config_version`

重跑规则：

1. reparse 不覆盖旧 parser run，旧 blocks / tables / ocr_spans 通过新 pipeline run 区分。
2. rechunk 不覆盖旧 chunk，旧 chunk 标记 `superseded` 或 `archived`。
3. reindex 只更新 embedding 状态和 Qdrant payload，不改变 chunk 文本。
4. fact_refresh 不覆盖 approved facts，新的 fact candidate 必须重新审核。
5. Prompt 和 content 重新生成必须创建新的 candidate / draft，旧产物标记 `superseded` 或保留为 archived。
6. 任一版本变化导致产物不可直接复用时，相关 embedding、fact、prompt、content 必须标记 `stale` 或 `needs_reextract`。

## 4. 页面信息架构

### 4.1 项目详情页一级入口

项目详情页保留 `知识库` 一级选项卡。

`知识库` 下拆成 6 个子选项卡：

1. `导入`
2. `处理任务`
3. `Chunk 可视化`
4. `事实质检`
5. `检索`
6. `知识库看板`

`Prompt` 一级选项卡下拆成 5 个子选项卡：

1. `Prompt 列表`
2. `Prompt 生成`
3. `候选审核`
4. `生成模板`
5. `导入记录`

`运营工作台` 或 `内容工作台` 中展示 GEO 文案生成和审核能力。

### 4.2 知识库导入页布局

`知识库 > 导入` 页面从上到下展示：

1. 来源类型选择；
2. 上传/抓取队列；
3. 解析策略；
4. 清洗与切分配置；
5. 预检查；
6. 提交导入任务；
7. 最近导入任务摘要。

页面不再把 URL、文本、CSV、解析、抽取、审核混在一个表单里。

## 6. GEO Adapter Output Contract

所有 parser / crawler adapter 必须输出统一的 GEO Parser Contract。系统内部不直接依赖 Docling、MinerU、Unstructured、Tika、MarkItDown 或 Crawl4AI 的原生结构。

### 6.1 统一输出结构

```json
{
  "adapter": {
    "engine": "docling",
    "engine_version": "x.y.z",
    "adapter_version": "geo-parser-adapter-v1"
  },
  "source_asset_id": "asset-id",
  "pages": [],
  "blocks": [],
  "tables": [],
  "images": [],
  "ocr_spans": [],
  "metadata": {},
  "quality_signals": [],
  "artifacts": []
}
```

强制要求：

1. Docling 输出必须映射到该 schema。
2. MinerU 输出必须映射到该 schema。
3. Unstructured 输出必须映射到该 schema。
4. Tika 即使只能输出纯文本，也必须包装成 block。
5. MarkItDown 输出 Markdown，也必须切成 block。
6. Crawl4AI 输出网页 HTML、Markdown、截图和 links 后，必须先创建 source asset，再进入 parser pipeline。
7. 所有 adapter 必须返回 `quality_signals`。
8. 所有 adapter 必须返回 `artifacts`，即使为空数组。

### 6.2 Block Contract

每个 block 至少包含：

- `block_id`
- `block_type`
- `text`
- `page_number`
- `section_path`
- `reading_order`
- `bbox`
- `confidence`
- `source_asset_id`
- `content_hash`
- `metadata`

允许缺失：

- Markdown / HTML 输入允许 `page_number=null`。
- Tika fallback 允许 `bbox=null`。
- 纯文本允许 `section_path=[]`。

### 6.3 Table Contract

每个 table 至少包含：

- `table_id`
- `block_id`
- `page_number`
- `caption`
- `row_count`
- `column_count`
- `cells`
- `markdown`
- `csv_artifact`
- `html_artifact`
- `confidence`
- `quality_signals`

允许缺失：

- caption 可缺失；
- bbox 可缺失；
- fallback adapter 可只提供 markdown table，但必须标记 `table_structure_low_confidence`。

### 6.4 OCR Span Contract

每个 OCR span 至少包含：

- `span_id`
- `text`
- `page_number`
- `bbox`
- `confidence`
- `language`
- `source_image_ref`
- `content_hash`

如果 OCR 只返回整页文本，必须包装为 page-level OCR span，并标记 `ocr_page_level_only`。

### 6.5 Adapter Capability Matrix

| 输入类型 | 首选 adapter | 第二 adapter | 兜底 adapter | 必须产物 | 允许缺失 |
| --- | --- | --- | --- | --- | --- |
| 普通 PDF | Docling | MinerU | Tika | blocks, pages, markdown | bbox 可缺 |
| 扫描 PDF | MinerU | Docling OCR | Tika | ocr_spans, pages | table structure 可缺 |
| 表格密集 PDF | MinerU | Docling | Tika | tables, csv/html artifacts | caption 可缺 |
| DOCX | Docling | MarkItDown | Tika | blocks, markdown | bbox 可缺 |
| PPTX | Docling | MarkItDown | Tika | slide blocks | detailed bbox 可缺 |
| XLSX/CSV | Docling/custom tabular | Tika | none | table chunks | prose blocks 可缺 |
| HTML | Docling | Unstructured | MarkItDown | blocks, links | screenshot 可缺 |
| Web URL | Crawl4AI + Docling | Crawl4AI + Unstructured | MarkItDown | html, markdown, screenshot | table csv 可缺 |
| Markdown | MarkItDown/direct | Unstructured | Tika | blocks | page number 可缺 |
| Image | MinerU/OCR | Docling OCR | none | ocr_spans | table structure 可缺 |

### 6.6 Fallback 规则

1. 首选 adapter 失败且输入类型有第二 adapter 时，自动 fallback。
2. fallback 成功时，`knowledge_parser_runs.status=fallback_succeeded`。
3. fallback 原因必须写入 parser run metadata。
4. 前端必须显示“指定引擎失败，已使用 fallback 引擎完成解析”。
5. fallback 产物必须通过同样的 quality gates。
6. 如果 fallback 只能产出纯文本，不允许直接进入高置信事实抽取，必须标记 `parser_low_structure_confidence`。

## 7. Quality Gate 机制

状态机之外，必须有阻断门禁。门禁结果决定 pipeline 是否继续、进入人工审核、partial success 或 failed。

### 7.1 Gate 类型

```text
pre_import_gate
parser_quality_gate
chunk_quality_gate
embedding_gate
fact_quality_gate
generation_quality_gate
traceability_gate
security_gate
publish_gate
```

### 7.2 Gate 结果

```text
passed
warning
blocked
accepted_risk
failed
```

| 状态 | 含义 |
| --- | --- |
| `passed` | gate 成功执行且无阻断问题 |
| `warning` | gate 成功执行，发现非阻断问题 |
| `blocked` | gate 成功执行，且发现阻断问题 |
| `accepted_risk` | 有风险但被授权用户接受 |
| `failed` | gate 自身执行失败，例如检查器报错、依赖不可用 |

### 7.3 阻断规则

| Gate | 阻断条件 |
| --- | --- |
| `pre_import_gate` | 文件超限、私有 URL、加密文件、空文件 |
| `parser_quality_gate` | 无正文、解析失败、OCR 全空 |
| `chunk_quality_gate` | chunk 无 source、chunk 过短比例过高、导航污染严重 |
| `embedding_gate` | active chunk embedding 大面积失败 |
| `fact_quality_gate` | fact 无证据、低置信度、事实冲突未处理 |
| `generation_quality_gate` | 使用 pending/rejected facts、缺 source refs |
| `traceability_gate` | 生成结果无法追溯到 source asset |
| `security_gate` | secret、PII、raw parser JSON 泄露风险 |
| `publish_gate` | 未经人工审核、证据缺失、引用缺失 |

### 7.4 Gate 对 pipeline 的影响

1. blocking gate 返回 `blocked` 时，pipeline stage 进入 `blocked`。
2. required stage 被 blocked 时，pipeline run 进入 `failed` 或 `waiting_human_review`。
3. 非 blocking gate 返回 `warning` 时，pipeline 可以继续，但必须生成 quality finding。
4. `accepted_risk` 必须由有权限用户确认，并写审计事件。
5. `traceability_gate` 和 `security_gate` 不允许自动 accepted risk。
6. `publish_gate` 未通过时，Prompt 可以继续处于候选态，文案不能发布或导出给客户。

`accepted_risk` 权限规则：

1. 只有 `project_admin`、`internal_operator`、`compliance_reviewer` 可以 accepted risk。
2. `customer_viewer`、普通 `editor`、只读 reviewer 不得 accepted risk。
3. accepted risk 必须记录 `accepted_by`、`accepted_at`、`reason`、`expires_at`、`affected_gate_run_ids`、`affected_finding_ids`。
4. accepted risk 到期后必须重新触发对应 gate，不能永久豁免。

## 8. API 规划

### 8.1 Pipeline 编排

输入：

- `run_type`
- `entry_source`
- `market_code`

5. 写审计事件 `knowledge.pipeline_run_created`。

启动 pipeline run。

行为：

1. 执行 `pre_import_gate`。
2. 通过后状态改为 `queued`。
3. 投递 orchestration worker。
4. 写审计事件 `knowledge.pipeline_run_queued`。

列表页，支持按 `project_id`、`run_type`、`status`、`entry_source` 过滤。

#### `GET /v1/knowledge/pipeline-runs/runtime/{id}`

详情页返回：

- pipeline run；
- stages；
- jobs；
- assets；
- parser runs；
- chunks summary；
- quality gate runs；
- fact / prompt / content summary；
- audit events。

#### `GET /v1/knowledge/pipeline-runs/runtime/{id}/stages`

返回某次 pipeline run 的 stage 列表、状态、错误、重试次数、是否 required / blocking，以及关联的 quality gate run 摘要。

#### `GET /v1/knowledge/pipeline-runs/runtime/{id}/jobs`

返回某次 pipeline run 下的 import、crawl、parser、chunk、embedding、fact extraction、prompt generation、content generation jobs，用于处理任务页和 worker logs 入口。

#### `POST /v1/knowledge/pipeline-stages/runtime/{id}/retry`

重试某个阶段。

限制：

1. 只能重试 `failed`、`blocked`、`retrying` 可恢复阶段。
2. 审核阶段不能通过 retry 绕过人工审核。
3. 重试必须写 audit event。

支持按 `project_id`、`pipeline_run_id`、`target_type`、`severity`、`status` 过滤，返回质量问题列表。

#### `GET /v1/knowledge/quality-gate-runs/runtime`

支持按 `project_id`、`pipeline_run_id`、`stage_id`、`gate_key`、`status` 过滤，返回 gate 执行结果和阻断原因。

#### `GET /v1/knowledge/trace-refs/runtime`

支持按 `project_id`、`pipeline_run_id`、`source_type`、`source_id`、`target_type`、`target_id` 过滤，返回 `knowledge_trace_refs`。

#### `GET /v1/knowledge/fact-candidates/runtime`

支持按 `project_id`、`pipeline_run_id`、`fact_kind`、`status`、`market_code`、`city` 过滤，服务事实质检队列。

#### `GET /v1/knowledge/prompt-candidates/runtime`

支持按 `project_id`、`pipeline_run_id`、`target_platform`、`intent_type`、`status` 过滤，服务 Prompt 候选审核。

#### `GET /v1/knowledge/content-drafts/runtime`

支持按 `project_id`、`pipeline_run_id`、`content_type`、`status`、`target_city` 过滤，服务内容工作台。

### 8.4 Chunk 与检索

#### `GET /v1/knowledge/chunks/runtime`

支持过滤：

- `project_id`
- `import_job_id`
- `source_asset_id`
- `chunk_type`
- `status`
- `quality_flag`
- `market_code`
- `city`
- `query`

返回：

- chunk；
- source asset；
- parser run；
- quality flags；
- qdrant score；
- `knowledge_trace_refs`。

#### `GET /v1/knowledge/chunks/runtime/{id}/trace`

返回完整链路：

```text
chunk
-> blocks
-> tables
-> parser_run
-> source_asset
-> import_job
-> quality_findings
-> facts
-> generated outputs
```

#### `POST /v1/knowledge/chunks/runtime/{id}/disable`

禁用 chunk。

行为：

1. 权限校验。
2. chunk 状态变为 `disabled`。
3. Qdrant payload 同步禁用。
4. 该 chunk 不能再进入事实抽取和生成上下文。
5. 写审计事件。

### 8.5 事实候选与审核

#### `POST /v1/knowledge/fact-extraction-jobs/runtime`

创建事实抽取 job。

输入：

- `project_id`
- `pipeline_run_id`
- `import_job_id`
- `fact_kinds`
- `max_facts`
- `model`
- `prompt_version`

行为：

1. 读取 active chunks。
2. 创建 `fact_extraction_jobs`。
3. 投递 worker。
4. worker 调用 DeepSeek v4 flash。
5. 输出 `knowledge_fact_candidates`。
6. 候选状态默认 `pending_review`。
7. 写 `knowledge_trace_refs`。

#### `POST /v1/knowledge/fact-candidates/runtime/{id}/review`

审核事实候选。

决策：

- approve；
- reject；
- archive；
- mark_forbidden；
- merge_into_existing；
- request_reextract。

行为：

1. approve 时写入或更新 `localized_knowledge_facts`。
2. rejected / archived / forbidden 不进入生成上下文。
3. 所有决策写审计事件。

### 8.6 Prompt 与内容生成

#### `POST /v1/knowledge/prompt-generation-jobs/runtime`

创建 Prompt 生成 job。

硬规则：

1. 只能读取 approved facts。
2. 只能读取 active chunks。
3. 必须写 `source_fact_ids` 和 `source_chunk_ids`。
4. 输出先进入候选审核，不直接写正式 Prompt。

#### `POST /v1/knowledge/content-generation-jobs/runtime`

创建 GEO 文案生成 job。

硬规则：

1. 只能读取 approved facts。
2. 草稿必须附证据引用。
3. 生成结果默认 `pending_human_review`。
4. 文案发布前必须经过人工审核。

## 9. Worker 规划

### 9.1 Orchestration Worker

职责：

1. 领取 `knowledge_pipeline_runs`。
2. 初始化和推进 `knowledge_pipeline_stages`。
3. 调度 import、crawl、parse、chunk、embedding、fact extraction、prompt generation、content generation。
4. 执行 quality gate。
5. 根据 stage 和 gate 结果更新 pipeline run 总状态。
6. 处理 retry、partial success、failed、waiting_human_review。

总状态推进规则：

```text
draft
-> ready
-> queued
-> running
-> waiting_human_review
-> succeeded / partial_succeeded / failed / cancelled
```

Orchestration Worker 不直接解析文件、不直接跑 OCR、不直接生成 Prompt。它只负责调度、状态、门禁和汇总。

### 9.2 Parser Worker

职责：

1. 领取 `knowledge_parser_runs`。
2. 按 Adapter Capability Matrix 选择 adapter。
3. 对文件或网页产物运行解析 adapter。
4. 将 adapter 输出转换为 GEO Adapter Output Contract。
5. 归档 parser JSON、Markdown、table artifacts、OCR debug JSON。
6. 写入 blocks、tables、ocr_spans、page_snapshots。
7. 运行 parser quality gate。
8. 通知 orchestration worker 推进阶段。

解析运行状态：

```text
queued
-> running
-> succeeded / fallback_succeeded / failed / cancelled
```

失败必须记录：

- `error_code`
- `error_message`
- `failed_step`
- `retryable`
- `source_asset_id`
- `fallback_from_engine`
- `fallback_reason`

### 9.3 Crawl Worker

职责：

1. 领取 `crawl_jobs`。
2. 使用 Crawl4AI 执行单 URL、多 URL、sitemap 或站点 depth crawl。
3. 校验 public URL、robots、allowlist、exclude。
4. 渲染 JS 页面。
5. 归档 HTML、Markdown、截图。
6. 创建 crawled source assets。
7. 为每个可用网页创建 parser run。
8. 允许 partial success。

### 9.4 Chunk Worker

职责：

1. 领取 `chunk_jobs`。
2. 读取 parser blocks、tables、ocr_spans。
3. 清洗 header/footer/nav/sidebar。
4. 按 chunk profile 切分。
5. 表格单独生成 table chunk。
6. 写入 `knowledge_chunks`。
7. 写 chunk quality findings。
8. 执行 chunk quality gate。

### 9.5 Embedding Worker

职责：

1. 领取 `embedding_jobs`。
2. 使用 BGE-M3 生成 embedding。
3. 写入 Qdrant collection `geo_knowledge_chunks`。
4. 更新 chunk `embedding_status`。
5. 同步 disabled/stale payload。
6. 执行 embedding gate。

### 9.6 Fact Extraction Worker

职责：

1. 领取 `fact_extraction_jobs`。
2. 读取 active chunks。
3. 调用 DeepSeek v4 flash。
4. 输出 `knowledge_fact_candidates`。
5. 写 `knowledge_trace_refs`。
6. 写 fact quality findings。
7. 将 pipeline 推进到 `waiting_human_review`。

### 9.7 Prompt Generation Worker

职责：

1. 领取 `prompt_generation_jobs`。
2. 只读取 approved facts 和 active chunks。
3. 调用 DeepSeek v4 flash。
4. 输出 prompt candidates。
5. 检测重复和风险。
6. 写 `knowledge_trace_refs`。
7. 执行 generation quality gate。

### 9.8 Content Generation Worker

职责：

1. 领取 `content_generation_jobs`。
2. 只读取 approved facts 和 active chunks。
3. 生成 GEO content drafts。
4. 写 citation refs。
5. 写 `knowledge_trace_refs`。
6. 执行 generation quality gate 和 publish gate。

### 9.9 Adapter 路由规则

#### 自动策略

`parser_strategy=auto` 时：

1. PDF / DOCX / PPTX / XLSX / HTML / image 默认走 Docling。
2. 扫描 PDF、复杂中文 PDF、表格密集 PDF、公式密集 PDF 走 MinerU。
3. 纯文本、Markdown、HTML 转文本走 Unstructured。
4. Docling 或 MinerU 失败后走 Tika。
5. 轻量 Office/HTML 快速转换可走 MarkItDown。

#### 手动策略

用户可在前端选择：

- 自动；
- Docling；
- MinerU；
- Unstructured；
- Tika；
- MarkItDown。

手动选择失败时仍允许 fallback，但页面必须显示：

```text
指定引擎失败，已使用 fallback 引擎完成解析
```

### 9.10 Crawl4AI Worker 步骤

站点爬取任务执行：

1. 读取 seed URL。
2. 校验 public URL。
3. 执行 robots/allowlist。
4. 按 depth 和 max_pages 限制抓取。
5. 对 JS 页面开启浏览器渲染。
6. 提取 title、HTML、Markdown、links。
7. 保存截图。
8. 记录 status code、content type、load time。
9. 每个页面创建 `knowledge_source_assets`。
10. 每个页面进入 Docling/Unstructured/MarkItDown 解析链路。

首版限制：

- 单任务最大 100 页；
- 默认 depth 2；
- 默认同域；
- 默认 respect robots；
- 默认阻断登录页、购物车、结账、账户页；
- 默认阻断 query 参数爆炸。

### 9.11 Chunk Worker 步骤

1. 读取 parser blocks。
2. 删除 header/footer/nav/sidebar。
3. 合并短标题和正文。
4. 表格单独作为 table chunk。
5. 长段落按 chunk profile 切分。
6. 保留 source block ids。
7. 写 `knowledge_chunks`。
8. 对低质量 chunk 写 `knowledge_quality_findings`。

默认 chunk profile：

- `chunk_size_tokens=500`
- `chunk_overlap_tokens=80`
- 表格不与正文混切；
- 标题路径保留；
- 每个 chunk 必须有 source asset；
- 每个 chunk 必须有 content hash。

### 9.12 Embedding Worker 步骤

1. 读取 `embedding_status=pending` 的 active chunks。
2. 使用 BGE-M3 生成 embedding。
3. 写入 Qdrant collection。
4. Qdrant payload 包含：
   - `project_id`
   - `pipeline_run_id`
   - `chunk_id`
   - `chunk_job_id`
   - `parser_run_id`
   - `import_job_id`
   - `market_code`
   - `locale`
   - `city`
   - `chunk_type`
   - `status`
   - `source_asset_id`
   - `embedding_model`
   - `embedding_model_version`
   - `content_hash`
   - `chunk_version`
5. 更新 `embedding_status=embedded`。
6. 失败时写 finding。

Qdrant collection 命名：

```text
geo_knowledge_chunks
```

## 10. 文件解析、OCR、表格抽取工作流

### 10.1 文件上传

用户操作：

1. 打开 `知识库 > 导入`。
2. 选择 `本地文件`。
3. 拖拽或选择文件。
4. 设置市场、语言、城市、标签。
5. 点击 `预检查`。

系统执行：

1. 前端用 Uppy 风格队列展示文件。
2. API 创建 import job。
3. API 上传文件到 MinIO。
4. API 创建 source asset。
5. 前端展示：
   - 文件名；
   - 类型；
   - 大小；
   - hash；
   - 上传状态；
   - 是否重复；
   - 是否支持解析。

### 10.2 解析预检查

系统检查：

1. 文件类型是否支持。
2. 文件大小是否超限。
3. 是否疑似扫描 PDF。
4. 是否表格密集。
5. 是否可能包含图片文字。
6. 是否存在密码保护。
7. 是否需要 OCR。
8. 是否可能包含敏感信息。

页面展示：

- `可直接解析`
- `需要 OCR`
- `建议 MinerU`
- `建议 Docling`
- `可能失败，Tika 兜底`
- `文件超限`
- `需要人工处理`

### 10.3 OCR

OCR 由 Docling 或 MinerU 执行。

OCR 输出：

- OCR text；
- page number；
- bbox；
- confidence；
- language；
- source image region；
- content hash。

质量规则：

- OCR 平均置信度低于 0.75，标记 `ocr_low_confidence`。
- 单页 OCR 文本低于 20 字且页面有图片，标记 `ocr_empty_page`。
- 乱码比例高，标记 `ocr_garbled_text`。
- OCR span 没有 page number 或 bbox，标记 `ocr_missing_location`。

### 10.4 表格抽取

表格由 Docling 或 MinerU 抽取。

每个表格必须输出：

- table markdown；
- CSV artifact；
- HTML artifact；
- row count；
- column count；
- page number；
- caption；
- source block id；
- confidence。

质量规则：

- 表格行列为空，标记 `table_empty`。
- 行列数异常，标记 `table_shape_suspect`。
- 表格被拆散，标记 `table_fragmented`。
- 表格没有 page number，标记 `table_missing_page`。
- 表格中的价格、日期、百分比字段无法识别，标记 `table_value_parse_risk`。

### 10.5 解析产物归档

每个 parser run 必须归档：

- 原始文件；
- parser JSON；
- parser Markdown；
- 表格 CSV；
- 表格 HTML；
- OCR 片段；
- 错误日志；
- 质量报告。

归档对象写入 MinIO，元数据写入 Postgres。

## 12. 品牌事实、竞品事实、市场事实工作流

### 12.1 事实类型

#### 品牌事实

类型：

- `warranty`
- `customer_support`
- `review_source`

用于描述竞品。

类型：

- `competitor_identity`
- `competitor_product_line`
- `competitor_selling_point`
- `competitor_pricing`
- `competitor_channel`
- `competitor_review_source`
- `competitor_weakness`
- `comparison_dimension`

#### 市场事实

用于描述本地市场。

类型：

- `market_requirement`
- `city_context`
- `local_policy`
- `consumer_concern`
- `seasonality`
- `language_variant`

#### 信源事实

用于评估引用来源。

类型：

- `source_authority`
- `source_type`
- `publication_date`
- `citation_availability`
- `source_gap`

### 12.2 抽取步骤

1. 用户在 `Chunk 可视化` 或 `处理任务` 点击 `抽取事实`。
2. 系统读取 active chunks。
3. 系统按 fact kind 组装模型输入。
4. DeepSeek v4 flash 输出结构化 JSON。
5. 系统校验 schema。
6. 系统创建 `knowledge_fact_candidates`。
7. 系统创建 `knowledge_trace_refs`。
8. 系统创建质量 findings。
9. 页面跳转到 `事实质检`。

### 12.3 审核门禁

硬规则：

1. 所有事实候选默认 `pending_review`。
2. 只有 `approved` 能进入 Prompt 生成。
3. `rejected`、`archived`、`forbidden`、`superseded`、`merged`、`needs_reextract` 不得进入生成上下文。
4. 事实审核必须写审计事件。
5. 审核页面必须展示原文证据。

审核操作：

- 批准；
- 拒绝；
- 归档；
- 标记禁用；
- 合并到已有事实；
- 要求重抽取。

### 12.4 冲突处理

冲突场景：

- 同一品牌政策不同；
- 同一产品价格不同；
- 竞品名称与品牌别名冲突；
- 事实过期；
- 市场/城市不匹配；
- 来源权威性不足。

处理规则：

1. 系统标记 `fact_conflict`。
2. 审核人选择保留哪条。
3. 被替代事实标记 `superseded` 或 `archived`。
4. 所有生成结果继续引用被保留事实。

## 15. GEO 文案生成工作流

### 15.1 触发方式

GEO 文案生成可从三个入口触发：

1. Action Plan；
2. 知识库 approved facts；
3. Prompt / 报告中的 source gap。

### 15.2 文案类型

首版支持：

- FAQ；
- 产品页段落；
- 类目页段落；
- 竞品比较页；
- 引用友好型说明段；
- 本地化购买指南；
- 客服问答；
- 证据补强 brief。

### 15.3 生成输入

必须包含：

- content type；
- target platform；
- target audience；
- target city；
- target facts；
- target action；
- tone；
- required citations；
- forbidden claims。

### 15.4 输出结构

每个 content draft 必须包含：

- title；
- markdown；
- summary；
- used_fact_ids；
- used_chunk_ids；
- citation_refs；
- risk_flags；
- generation_prompt_version；
- model；
- output_hash；
- review_status；
- created_by；
- created_at。

### 15.5 审核流程

状态：

- `pending_human_review`
- `approved`
- `rejected`
- `needs_revision`
- `published`
- `exported`
- `archived`

`approved` 只表示审核通过；`published` 表示已对外发布；`exported` 表示已导出为可交付资产。三者不能互相替代。

审核页面展示：

- 文案；
- 事实引用；
- chunk 证据；
- 风险标签；
- 模型；
- 模板版本；
- 审计事件。

发布前必须 approved。

## 16. 证据追踪

### 16.1 追踪链路

所有生成结果必须能追溯到原始证据。

标准链路：

```text
SourceFile / CrawledPage
-> RawAsset
-> ParserRun
-> KnowledgeBlock / KnowledgeTable / OCRSpan
-> KnowledgeChunk
-> KnowledgeFactCandidate
-> ApprovedKnowledgeFact
-> PromptCandidate / ContentDraft
-> OfficialPrompt / Report / Action / Retest
```

### 16.2 页面展示

在 Prompt 候选、文案草稿、事实审核、chunk 可视化中都要提供 `查看证据链`。

证据链弹窗展示：

1. 原始文件或 URL；
2. parser engine；
3. page number；
4. chunk；
5. fact；
6. generated output；
7. audit events。

### 16.3 证据规则

禁止：

- 无 source chunk 的事实进入 approved；
- 无 approved fact 的 Prompt 候选导入正式 Prompt；
- 无 fact 引用的 GEO 文案进入 approved；
- raw secret 出现在证据链；
- customer viewer 访问内部 raw parser JSON。

## 20. 完成定义

本工作流完成时，必须满足：

1. 用户可以从前端导入文件和站点。
2. 文件解析、OCR、表格抽取由开源 adapter 完成。
3. 解析产物可在前端查看。
4. chunk 可视化可用。
5. Qdrant 检索可用。
6. 品牌事实和竞品事实可抽取、审核、追踪。
7. 只有 approved facts 可进入生成。
8. Prompt 候选可生成、审核、导入。
9. GEO 文案可生成、审核、导出。
10. 任一生成结果都能追溯到原始文件或网页。
11. 全流程 smoke 和前端点击测试通过。

只存在 API、没有前端入口，不算完成。

只生成内容、不能追溯证据，不算完成。

只完成 CSV/文本，不支持文件解析和站点爬取，不算完成。

只使用 fixture，不接真实 worker / object store / Qdrant，不算完成。
