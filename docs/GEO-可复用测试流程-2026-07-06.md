## 1. 测试总原则

本项目不能只用“单元测试通过”判断可用。任何面向真实客户的能力，必须同时满足：

1. 后端 API / Repository / DB 契约可验证。
2. 前端页面有明确入口，用户能完成操作。
3. 权限、审计、密钥脱敏和负向访问被覆盖。
4. 关键业务数字能追溯到证据链。
5. 真实或准真实 smoke 产物可复现。

测试产物默认写入 `tmp/*/latest.json`。截图、临时 JSON、trace、smoke 输出默认不提交，除非明确要求归档。

新增改动必须同步测试：

- 新增 API 必须补 API contract 或 e2e smoke。
- 新增 DB 表、字段、SQL 查询必须补 Repository/Core contract 或 DB smoke。
- 新增前端页面或交互必须补页面点击 smoke 或 UI contract smoke。
- 新增权限、token、session、邀请、客户入口必须补安全和负向访问测试。
- 新增报告、评分、证据链必须补 traceability 测试。
- 新增 connector、模型调用、外部 API 必须补真实或 recorded connector smoke。
- 新增知识库、内容生成、效果验证能力必须补知识库应用和业务闭环测试。

## 2. 后端可复用测试流程

### 2.1 快速后端回归

适用：普通 Python 逻辑、Repository 小修、API 参数修复。

```bash
make lint-python
make compile-python
make test
```

通过标准：

- 无 lint error。
- Python 文件可编译。
- `tests/` 全量 unittest 通过。

### 2.2 API / Repository / SQL 变更回归

适用：FastAPI route、Repository、SQL、migration、RLS 上下文、分页/过滤/排序。

```bash
PYTHONPATH=packages/geo_core:apps/api python3 -m unittest tests.test_api_contracts
PYTHONPATH=packages/geo_core:apps/api python3 -m unittest tests.test_core_contracts
PYTHONPATH=packages/geo_core:apps/api python3 -m unittest tests.test_repository_boundaries
make db-smoke
```

必查项：

- SQL placeholder 数量与参数一致。
- 动态 SQL 片段不能留下未格式化的 `{...}`。
- 旧数据和空数据都不触发 500。
- list/detail/filter 场景都返回稳定 JSON。
- migration 必须 additive 优先，不能无保护破坏已有表。

### 2.3 权限、安全、审计回归

适用：AuthContext、session、邀请、客户门户、报告下载、证据下载、provider key。

```bash
make rls-smoke
make security-smoke
make no-secret-leak-smoke
make customer-access-negative-smoke
```

通过标准：

- 跨租户、跨项目、未发布、已撤回、raw evidence、provider key 访问必须失败。
- API response、日志、前端 bundle、报告、测试产物不得出现 raw secret、raw invite token、raw session token。
- 关键动作必须写入审计事件。

### 2.4 报告、评分、证据链回归

适用：AnswerAnalysis、评分公式、ScoreContribution、ReportExport、PDF/CSV/Markdown、EvidenceAsset。

```bash
make report-traceability-smoke
make production-v1-e2e
```

通过标准：

- 报告中的数字能追溯到 `ScoreContribution -> AnswerAnalysis -> RawAnswer -> EvidenceAsset`。
- Markdown、PDF、CSV 来自同一个固定 snapshot。
- 已发布报告可下载，撤回后客户不能下载。
- 报告不得包含 provider key、raw token 或未经授权的 raw payload。

### 2.5 Connector 和模型调用回归

适用：OpenAI、Perplexity、Google manual backfill、DeepSeek 临时真实问答 smoke。

```bash
make connector-real-smoke
```

当前默认真实问答 smoke：

- provider：DeepSeek
- endpoint：`https://api.deepseek.com/chat/completions`
- model：`deepseek-v4-flash`
- key source：`deepseek_api_key.txt`
- output：`tmp/connector-real-smoke/latest.json`

通过标准：

- 真实 HTTP 请求返回 200。
- response 有可用 answer 和 usage。
- 产物只记录 key hash prefix，不记录 raw key。
- 如果改 OpenAI / Perplexity / Google 生产 connector，必须补对应 provider 的 recorded contract 测试；staging / production-internal 还必须跑真实 provider 子集。

## 4. 真实店铺项目测试流程

本流程用于验证一个真实业务项目是否真的能从 0 跑通。当前系统中，“店铺”按 “GEO 项目 + 品牌 + 官网域名 + 产品线 + 竞品 + 客户入口” 建模，不新增独立 shop 表。

### 4.1 测试数据

每次测试使用全新唯一后缀，避免污染已有项目。

必填数据：

- 店铺/品牌名：例如 `LifecycleSmoke{timestamp}`。
- 官网域名：例如 `lifecyclesmoke{timestamp}.example.com`。
- 市场：`AU`。
- 城市：`Sydney`、`Melbourne`。
- 语言：`en-AU`。
- 产品线：例如 `Air purifier`、`Weighted blanket`。
- 竞品：至少 3 个，例如 `BrightNest`、`KoalaLab`、`HarbourHome`。
- 客户邮箱：例如 `customer+{timestamp}@example.com`。

### 4.2 创建店铺项目

推荐命令：

```bash
make full-project-lifecycle-smoke
```

该 smoke 已覆盖：

- 创建项目。
- 读取项目。
- 修改项目。
- archive / restore。
- 非法项目动作负向测试。
- 品牌和竞品创建/更新。
- 项目成员增删。
- 邀请撤销和重新生成。

通过标准：

- 项目在 `/projects` 可见。
- 项目详情可打开。
- 项目名、品牌、竞品、市场、prompt 数量在看板和详情页一致。
- 被撤销的邀请不能兑换。
- 新邀请只显示一次 raw token。

### 4.3 配置 Prompt

测试动作：

- 导入 prompt CSV。
- 验证 prompt 数量增加。
- 编辑一条 prompt。
- 导出 prompt CSV。
- 导入错误 CSV，确认返回 400。

推荐命令：

```bash
make full-project-lifecycle-smoke
```

通过标准：

- `prompt_import.prompt_count` 大于 0。
- `/v1/prompts/runtime` 返回新 prompt。
- 项目看板 prompt 数量同步更新。
- 错误 CSV 不写入脏数据。

### 4.4 导入知识库

测试动作：

- 导入知识库 CSV 或文档。
- 搜索 approved facts。
- 验证 draft / forbidden / deprecated facts 不进入生成。
- 导入错误知识库 CSV，确认返回 400。

推荐命令：

```bash
make full-project-lifecycle-smoke
make knowledge-application-smoke
```

通过标准：

- `knowledge_import.fact_count` 大于 0。
- `/v1/knowledge-facts/runtime/search` 能查到相关事实。
- 只有 approved facts 被内容生成和 prompt 生成使用。
- 错误 CSV 不污染知识库。

### 4.5 基于知识库生成 GEO 文案和问答 Prompt

测试动作：

- 使用 approved facts 生成 GEO 文案 brief 或 draft。
- 生成 FAQ answer candidates。
- 生成 prompt candidates。
- 人工审核 prompt candidates。
- 将通过审核的 prompt candidates 导入正式 prompt。

推荐命令：

```bash
make knowledge-application-smoke
make promptfoo-knowledge-eval
make enablement-v1-e2e
```

通过标准：

- 生成内容包含知识库事实来源。
- 不引用 draft / forbidden facts。
- 生成 prompt 可导入正式 prompt 列表。
- DeepSeek `deepseek-v4-flash` smoke 至少返回有效答案。

### 4.6 采集 / Google manual backfill

测试动作：

- 对 prompt 做 Google manual backfill。
- 填入 answer、citation URLs、截图 URL、HTML snapshot URL。
- 批量导入 manual backfill CSV。
- 对不存在的 prompt 做补录，确认返回 404。

推荐命令：

```bash
make full-project-lifecycle-smoke
make connector-real-smoke
```

通过标准：

- 生成 answer_run。
- 生成 raw answer。
- 生成 citation。
- 生成 EvidenceAsset。
- 负向补录不产生垃圾记录。

### 4.7 分析、评分、报告

测试动作：

- 自动生成 AnswerAnalysis。
- 生成 VisibilityScoreSnapshot。
- 生成 ScoreContribution。
- 生成 Markdown / PDF / CSV 报告。
- 审批、发布、撤回报告。
- 客户门户查看和下载报告。

推荐命令：

```bash
make report-traceability-smoke
make customer-access-negative-smoke
make production-v1-e2e
```

通过标准：

- 报告数字可追溯。
- 发布后客户可下载。
- 撤回后客户不能下载。
- 跨项目客户不能下载。

### 4.8 Action Plan 和 Retest

测试动作：

- 生成至少 3 类行动建议：
  - brand not mentioned。
  - competitor outranks brand。
  - missing / weak citation source。
- 每条建议关联 evidence 或 score contribution。
- 创建 retest。
- 复测后展示 before_score、after_score、delta。

推荐命令：

```bash
make production-v1-e2e
make full-project-lifecycle-smoke
```

通过标准：

- Action 默认不对客户展示。
- 人工更新 owner/status 可保存。
- Retest 生成新 snapshot。
- 分数变化能追溯到 evidence。

## 5. 知识库导入与效果验证流程

该流程用于判断“导入知识库是否真的改善 GEO 项目效果”，不是只验证接口能跑。

### 5.1 基线采样

先在知识库导入前运行一批固定 prompt，记录：

- answer_present。
- brand_mentioned。
- brand_recommended。
- competitor_mentions。
- citation_domains。
- citation_count。
- total_score。
- score contribution。

产物必须包含：

- prompt set id 或 prompt_version。
- collection run id。
- score snapshot id。
- report export id。

### 5.2 知识库干预

导入和审核知识库：

- 品牌基础事实。
- 产品线事实。
- 售后、配送、保修、评价、证据页面。
- 竞品差异化事实。
- 禁用或废弃事实。

随后生成：

- GEO 文案建议。
- FAQ answer candidates。
- prompt candidates。
- Action Plan。

验收要求：

- approved facts 被使用。
- forbidden facts 不被使用。
- 每条生成内容能看到事实来源或 evidence 关联。

### 5.3 复测

用同一 prompt set 再跑一次：

- 同市场。
- 同城市。
- 同语言。
- 同平台或明确记录平台差异。
- 同评分公式版本。

输出：

- before_score。
- after_score。
- delta。
- 改善或下降原因。
- 引用来源变化。
- 竞品相对位置变化。

### 5.4 效果验收

必须通过：

```bash
make report-traceability-smoke
make production-v1-e2e
make enablement-v1-e2e
```

业务验收口径：

- 不能只看总分，必须看 mention、recommendation、citation、competitor delta。
- 所有提升都必须能追溯到原始 answer 和 evidence。
- 如果没有提升，系统必须能展示原因：未触发、未提及、竞品更强、citation 弱、知识事实不足、补录缺失。
- 不允许用 fixture/demo 数据冒充效果提升。

## 7. 最终验收流程

正式验收前按顺序执行：

```bash
make production-v1-progress
make full-project-lifecycle-smoke
make frontend-page-click-smoke
make frontend-knowledge-click-smoke
make connector-real-smoke
make knowledge-live-pipeline-smoke
make geo-production-full-pipeline-smoke
make knowledge-component-probe
make production-v1-final-gate
```

知识库验收必须区分两类结果：

- `geo-production-full-pipeline-smoke` / live E2E 通过，只能说明业务编排链路已跑通，包括项目、上传、对象存储、worker、chunk、Qdrant、事实抽取和 trace。
- `knowledge-component-probe` 中 Docling、MinerU、Unstructured、MarkItDown、Tika、Crawl4AI、BGE-M3 全部通过，才允许宣称“文件解析、OCR、表格抽取、网页抓取和本地 embedding 组件本体都跑通”。

重组件运行必须设置 `HF_HUB_OFFLINE=1` 和 `TRANSFORMERS_OFFLINE=1`，并只读挂载完整本地模型目录。模型存在时不得先尝试访问外网；模型缺失时必须立即失败，不能等待网络超时后静默降级。Docling HTML/PDF smoke 的默认 240 秒超时保持为硬门禁。

`knowledge-heavy-components-smoke` 默认复用已经通过组件探针的 `geo-knowledge-heavy:local`，仅在镜像不存在或显式设置 `KNOWLEDGE_HEAVY_REBUILD=1` 时重建。`knowledge-live-pipeline-smoke` 必须先通过 `workers/knowledge_worker/Dockerfile.runtime` 从该本地基础镜像复制当前 `apps/api`、`packages/geo_core`、`workers` 和组件脚本，生成 `geo-knowledge-worker:local`；不得直接运行可能包含旧业务代码的历史 worker 镜像。

`make knowledge-qdrant-smoke` 优先使用显式 `QDRANT_URL`；未提供时读取 `tmp/docker-compose.auto-ports.env` 并写入 `tmp/knowledge-qdrant-smoke-latest.json`。不得把固定 `6333` 或 `18006` 端口写死到测试流程。

如果业务链路通过但组件探针显示 `heavy_component_status=incomplete`，必须如实记录为：当前使用 fallback parser 或 deterministic embedding 跑通，不得把 fallback 结果冒充成熟开源组件已生产可用。

知识库 live E2E 除规划固定的 36 项验收外，还必须通过运行契约检查：

- 重复文件创建新的版本化 Source Asset，但复用同一个对象存储 URI；
- `pasted_text` 与 `csv_content` 直接 API 字段均通过预检；
- Pipeline 详情聚合 Stage、Job、Asset、Parser、Chunk、Gate、候选、汇总和审计；
- Import 详情聚合 Asset、Parser、Chunk、Finding、Fact 和审计；
- Pipeline、Import、Chunk、Fact Candidate、Prompt Candidate、Content Draft、Gate、Trace 的组合筛选返回目标记录；
- 任何运行契约失败都使 `run_knowledge_pipeline_live_e2e.py` 和总 smoke 返回非零状态。

知识库前端验收拆为两层：`frontend-page-click-smoke` 负责 desktop/mobile 逐页渲染和无副作用控件，`frontend-knowledge-click-smoke` 负责使用真实项目、真实 API 和真实 knowledge worker 执行业务变更。两者都必须通过。

逐页 Playwright smoke 必须执行以下交互，而不只是打开页面：

- 文件导入页选择两个不同格式文件并出现逐文件预检队列；
- Chunk 页填写正文筛选、生命周期和 Chunk 类型，提交后 URL 保留筛选参数；
- 选择 Chunk 打开证据面板；
- 在事实抽取表单选择来源 Pipeline、Chunk 类型、事实类型和候选上限；
- 在 Prompt 生成页选择已发布模板，并设置事实类型、市场、Chunk 类型和正文范围；
- 在内容工作台设置文案类型以及 Action、Report、Retest、Source Gap 关联字段；
- 页面不得出现 React/Next.js error overlay、hydration error、重复 key、500 资源错误或空白主区域。

知识库生命周期 Playwright 必须执行：

- 从 full-pipeline artifact 读取真实项目；
- 前端提交文本来源并创建/启动 Pipeline；
- 打开处理任务页验证 Stage、Job、Asset 和 Parser；
- 通过前端批准 Pipeline Fact Candidate；
- 通过前端创建 Prompt Generation Job，调用真实 worker；
- 通过前端编辑后批准 Prompt Candidate 并导入正式 Prompt；
- 通过前端创建 Content Generation Job，调用真实 worker；
- 通过前端批准文案并下载非空 Markdown；
- 通过前端提交知识库检索；
- 任一 action error、console error 或 HTTP 5xx 均使 smoke 失败。

## 8. 故障排查顺序

出现问题时按以下顺序定位：

1. API 500：先看 API traceback，定位 route 和 repository 方法。
2. SQL 错误：检查 placeholder 数量、未格式化 `{...}`、migration 是否已执行。
3. DB/RLS：确认 actor header、project scope、tenant scope、RLS current setting。
4. Server Action：确认前端 action 是否吞掉 API 错误。
5. 前端页面：检查 hydration mismatch、console error、error overlay、空页面。
6. 权限问题：跑 `customer-access-negative-smoke`，确认不是误放权。
7. 报告/评分问题：跑 `report-traceability-smoke`，抽查数字链路。
8. 知识库效果问题：确认 facts 状态、prompt set、baseline snapshot、retest snapshot 是否一致。
9. Connector 问题：确认 key 文件、provider endpoint、timeout、rate limit、返回结构和脱敏。
10. 最后再跑 full lifecycle 或 final gate，避免一开始被长链路噪声淹没。
