# 项目架构与代码治理整改方案

> 审查日期：2026-07-15
>
> 审查范围：应用代码、核心包、Worker、API 契约、数据库迁移、前端、测试、Compose/Make、项目文档和 Git 历史
>
> 文档状态：整改前审计基线，不描述当前实现；实际进度以 [整改执行状态](remediation-status.md) 和自动化证据为准
>
> 核心原则：先冻结行为和兼容合同，再做机械拆分；禁止直接全局改名或一次性重写

## 1. 执行结论

用户提出的五个问题全部真实存在。其中，“README 没有目录说明”需要修正为：README 有目录说明，但内容已经过时且与当前实现不一致；“所有 `GEO` 都是错误命名”也需要修正为：新产品和新技术合同应统一使用 `GEO`，但历史文档、持久化标识和已发布合同不能直接无差别替换。

当前代码可以运行，也具备 RLS、审计、OpenAPI 快照、数据库烟测、前后端构建等质量基础，但架构已经进入明显的“可运行但难演进”状态。最主要的风险不是单个函数写得不好，而是在线 API、离线脚本、Worker、持久化、阶段验收和演示 Fixture 被放进了同一依赖图。

整改优先级如下：

| 优先级 | 主题 | 结论 |
| --- | --- | --- |
| P0 | 本地 Secret 权限和启动环境隔离 | 立即修正，不等待大重构 |
| P1 | API/Repository 超大文件和错误依赖方向 | 必须拆分，是后续所有改动的前置条件 |
| P1 | 阶段名、Fixture 和内部运维接口进入生产 API 面 | 必须从产品 API 中隔离 |
| P1 | `GEO/GEO` 命名双轨 | 需要 ADR、兼容清单和分阶段迁移 |
| P1 | 数据库迁移无统一 ledger/checksum | 存在环境漂移风险，必须收口 |
| P1 | GEO 模型生成同步执行且位于 Repository | 存在超时、重试和职责混乱风险 |
| P1 | 测试大量绑定源码文本 | 会阻碍安全重构，应转向行为和契约测试 |
| P2 | 文档、目录、遗留前端和运维脚本管理 | 必须整理，但不应阻塞 P0/P1 修复 |
| P2 | 注释、Docstring 和架构说明不足 | 按公共边界和复杂不变量补齐，不做无意义注释灌水 |

- 变更热点前列包括 `README.md`、`PROJECT-PLAN.md`、工程审计日志、`apps/api/geo_api/main.py` 和 `packages/geo_core/geo_core/repository.py`。

### 2.4 API 与阶段术语泄漏

- `main.py:196-341` 直接导入 38 个 `scripts.*` 模块；`main.py:191` 还导入 Worker 私有函数。在线应用因此依赖仓库脚本目录和 Worker 内部实现。

### 2.5 命名扩散

在 `apps/packages/workers/scripts/infra/contracts` 中：

- 大小写不敏感的 `geo` 约出现 5,552 次；独立 `geo` 约出现 386 次。
- Python 包为 `geo_core`，API 包为 `geo_api`。
- OpenAPI 文件为 `contracts/openapi/geo-api.openapi.json`。
- 环境变量、Header、Cookie、数据库名、数据库角色、对象存储 bucket 和日志 logger 大量使用 `GEO_*` 或 `X-GEO-*`。
- `pyproject.toml` 的项目名仍为 `geo-saas-au`，描述也使用 GEO。

这不是一次文本替换可以解决的问题，而是已经形成外部合同、部署合同、包导入和持久化标识的系统性命名债务。

## 3. 对用户提出五项问题的逐项判定

### 3.1 耦合度过高：成立，且是首要架构问题

`main.py` 同时承担：

- FastAPI app 创建和生命周期；
- 鉴权、JWT/JWKS、Session、CSRF 和访问日志；
- 88 个请求模型；
- 265 个业务/运维/演示路由；
- 文件系统 artifact 读取与生成；
- 外部 HTTP 调用；
- 项目、采集、评分、报告、知识库、通知和 GEO 文案编排；
- 对 `scripts` 与 Worker 私有实现的直接调用。

`repository.py` 则将 20 多个领域的 SQL、事务、映射、业务判断和第三方模型调用集中在 `PostgresEvidenceRepository`。Repository 已经不是持久化适配器，而是事实上的 God Object。

现有 `auth_routes.py`、`ops_routes.py`、`runtime_access_routes.py` 证明项目已经开始模块化，但拆分只覆盖少部分路由，尚未形成统一模式。

### 3.2 `GEO/GEO` 命名不统一：成立，但需要兼容迁移

目标产品应明确使用 `GEO`。新代码继续引入 `GEO` 会扩大债务，应立即禁止。但以下内容不能直接全局替换：

- 已发布 Header、Cookie 和环境变量；
- Python import path；
- 数据库、角色、GUC、表内 method/version 字符串；
- S3 bucket/key、审计事件、hash 输入；
- 历史研究材料与归档文档。

这些标识参与外部调用、持久化或 hash 时，直接替换会造成兼容性中断或审计链失效。

### 3.3 对外暴露开发阶段：成立，范围比示例更大

`p0a/p0b/fixture/runtime` 是实现、阶段或测试语义，不是稳定业务资源。它们进入生产 OpenAPI 会带来：

- 客户误以为阶段接口是长期产品合同；
- 前端和集成方开始依赖临时路径；
- 内部 artifact 文件路径和交付状态被在线 API 绑定；
- 后续删除或改名成为 breaking change；
- 开发 Fixture 与真实业务数据语义混淆。

生产关闭 dev tools 只能阻止部分执行，不能解决接口合同污染。

### 3.4 注释和文档不足：成立

缺失最明显的不是普通赋值语句注释，而是以下边界：

- API 的权限、幂等、错误语义和副作用；
- Repository 的事务边界、锁、外部调用和 commit 时机；
- Durable Job 的 lease、retry、replay 和 dead letter 语义；
- 内容状态机、Claim 完整性和审批失效规则；
- RLS/GUC 与应用鉴权的职责分工；
- 数据迁移和兼容窗口。

当前 OpenAPI 主要依赖函数名和模型自动生成，缺少面向调用方的 summary、description、稳定 error contract 和 deprecated/sunset 说明。

### 3.5 文件和文档管理混乱：成立

README 在 `## 目录结构` 下仍只描述 `apps/api` 和 `apps/web`，没有正确描述 `admin-web`、`customer-web`、退役的 `dashboard-web`、GEO v3 模块、Worker 和大量运维工具。

`ARCHITECTURE.md` 最后更新于 2026-06-10，仍称仓库是“文档与规划项目”，并声明“上层只依赖下层接口”；当前 API 直接导入 `scripts` 和 Worker，实际实现已经违反该声明。

根目录存在 `ARCHITECTURE.md`、`PROJECT-PLAN.md` 和 208 KB 的 README；README 被持续追加进度和变更说明，已经同时承担入口说明、状态日志、架构说明、运行手册和 changelog。`docs/` 顶层也混放设计方案、运行手册、日期进度报告和当前规范。

## 4. 新发现的重大问题

### 4.1 P0：本地 DeepSeek Secret 权限过宽

根目录 `deepseek_api_key.txt` 被 Git 正确忽略，但当前文件权限为 `0664`；同机其他用户可读。相比之下，两个 `.env.au-*` 文件已经是 `0600`。

立即措施：

1. 将现有文件权限改为 `0600`；
2. 移至统一的 `secrets/` 或系统 Secret Manager，不再放在仓库根目录；
3. Compose 只接受 `*_FILE`；
4. CI/启动 preflight 检查 secret 未被 Git 跟踪、权限不超过 `0600`；
5. 如果该文件曾进入日志、备份或共享目录，轮换 Key。

生产 overlay 已使用 Docker secret 文件并关闭 dev tools，这是当前安全设计中的正面基础。风险主要来自本地文件权限和误用基础 Compose 作为生产配置。

### 4.2 P1：在线 API 依赖离线脚本和 Worker 私有函数

API 对 `scripts.*` 的 38 个直接 import，以及对 Worker `_collectors/_persist_records` 等私有实现的 import，违反依赖方向：

```text
期望：API -> Application Service -> Port <- Adapter/Worker/CLI
当前：API -> scripts + Worker private functions + Repository + external HTTP
```

后果包括容器必须携带整仓脚本、脚本重命名会导致 API 启动失败、离线 artifact 写盘进入在线请求、Worker 内部改动破坏 API。

### 4.3 P1：数据库迁移存在双轨和漂移风险

`schema-v2` runner 已有 `schema_migration_ledger + checksum`，但默认 `infra/docker-compose.yml` 的 `db-migrate` 仍在每次启动顺序重跑 `0011-0031`。这要求所有历史迁移永远保持幂等，并允许修改旧 migration 后在下一次启动重新执行。

需要统一为一个迁移机制：

- 每个 migration ID 只执行一次；
- 已执行 migration checksum 不允许变化；
- 变更必须新增 migration；
- 支持 expand/contract 和可审计的 rollback/forward-fix；
- 应用启动不再通过反复执行全部 SQL 来“碰运气收敛”。

### 4.4 P1：同步模型调用位于 Repository

`packages/geo_core/geo_core/geo_placement.py:365-432` 在 `GeoPlacementRepository.generate_package()` 中直接调用 DeepSeek。它同时负责查询、Prompt 渲染、外部付费调用、Claim 处理和 INSERT。

主要风险：

- API 请求生命周期绑定模型延迟；
- 进程中断后的恢复和计费语义不完整；
- Repository 无法保持“只负责持久化”的边界；
- 重试、fallback、调用预算和幂等难以集中治理；
- 无法自然提供 Job 查询、取消、lease/replay 和 dead letter。

应迁移为 Durable Generation Job；API 创建 Job，Worker 冻结输入后调用 Gateway，最后在事务中完成结果与 Job 状态。

### 4.5 P1：测试套件对源码文本绑定过深

- 57 个测试文件会直接读取源码文本；
- 测试目录约有 5,005 个 `assertIn`，其中既有合理的 payload 断言，也有大量源码字符串和命令清单断言；
- `test_core_contracts.py` 17,180 行，`test_api_contracts.py` 12,425 行。

这会让“移动函数到新模块”即使没有行为变化也触发大面积测试失败，从而反向鼓励继续向超大文件追加代码。

需要保留的测试：OpenAPI 快照、行为合同、数据库隔离、状态机、幂等、迁移和浏览器工作流。需要逐步替换的测试：实现文件路径、源码字符串、私有函数位置和完整命令数组顺序。

### 4.6 P2：运维入口成为第二个单体

944 行 Makefile、206 个 target 和 1,000 行 Compose 表明运维合同也集中在少数大文件。大量 `au-p0a-*`/`au-p0b-*` target 是阶段交付工具，不应长期占据产品级默认入口。

建议将 target 分组到 `make/*.mk`，Compose 拆成 base/dev/production/observability/worker profiles，并由顶层 Makefile 只暴露稳定命令。

### 4.7 P2：遗留前端和重复 BFF 代码形成双真源

- `apps/web` 已声明遗留但仍有 15,768 行 `ops/page.tsx`；
- `apps/dashboard-web` 已退役但仍保留构建目录和依赖；
- Admin/Customer 的 auth BFF route 大部分重复，仅 surface 和 landing 不同；
- Admin 的 `ProjectActions.tsx` 和 `page.tsx` 已再次变成聚合文件。

遗留应用应设定删除日期；共享认证 BFF、API client、错误映射和 Session 恢复逻辑应进入共享前端包。

### 4.8 P1：知识集中和评审能力不足

Bus Factor=1 意味着架构知识、运维步骤和隐含约束都集中在单人。对高审计要求系统，仅靠更多文档仍不足以替代第二人评审、CODEOWNERS 和可执行 ADR。

## 5. 目标架构

采用渐进式模块化单体，不立即拆微服务。先把依赖方向和边界修正，只有在独立扩缩容、故障隔离或团队所有权明确时再拆服务。

边界规则：

1. Router 只做 HTTP 映射、鉴权依赖和 DTO 转换；
2. Application Service 管理用例、状态机和事务意图；
3. Domain 不 import FastAPI、psycopg、httpx、scripts 或 workers；
4. Repository 只做持久化和映射，不调用模型；
5. Gateway 封装外部模型/HTTP；
6. CLI、Worker 和 API 都调用 Application Service，不互相 import；
7. `tools/fixtures` 不进入生产镜像和生产 OpenAPI。

## 6. 命名统一方案

### 6.1 规范

- 产品、UI、API title、文档和新代码统一使用 `GEO`。
- Python 新包使用 `geo_api`、`geo_core`。
- 新环境变量使用 `GEO_*`，新 Header 使用 `X-GEO-*`。
- 新 OpenAPI 文件使用 `geo-api.openapi.json`。
- `p0a/p0b` 只能出现在 `tools/`、历史计划和内部执行记录，不进入产品 DTO/URL。
- `runtime` 不再作为所有资源的通用 URL 后缀；资源本身应表达稳定业务含义。

### 6.2 兼容步骤

1. 新增 `docs/decisions/ADR-GEO-命名与兼容策略.md`，列出每个可见标识；现有根目录 `decisions/` 随文档整理迁入该目录；
2. 新代码只生成 `GEO` 名称；CI 对非 allowlist 的新增 `GEO` 报错；
3. 环境变量先读 `GEO_*`，缺失时回退 `GEO_*` 并记录 deprecation warning；
4. Header/Cookie 在一个明确版本窗口内双读，输出只使用新名称；
5. Python 提供临时 `geo_core -> geo_core` import shim；
6. OpenAPI 发布 v2，v1 进入冻结兼容模式；
7. 数据库物理名最后处理，优先通过 view/role alias 迁移；
8. 历史文档、审计事件和已有 hash 输入保持原样，不批量改写。

建议兼容窗口为两个可部署版本；具体时间必须在 ADR 中锁定，不能无限保留双轨。

## 7. API 整改方案

### 7.1 产品 API

产品 API 只保留稳定资源，例如：

```text
/v2/projects
/v2/projects/{project_id}/campaigns
/v2/campaigns/{campaign_id}/queries
/v2/campaigns/{campaign_id}/placement-opportunities
/v2/placement-packages/{package_id}/versions
/v2/generation-jobs/{job_id}
/v2/reviews/{review_id}
```

### 7.2 内部运维 API

确有在线读取价值的内部状态放入独立 internal app 或独立 router：

```text
/internal/ops/launch-readiness
/internal/ops/dependency-clearance
/internal/ops/retest-schedules
```

## 9. 分阶段实施计划

### Phase 0：安全与冻结基线（1-2 天）

1. 修正 DeepSeek secret 权限和存放位置；
2. 生成当前 OpenAPI、数据库 schema、关键行为和浏览器 Golden Baseline；
3. 增加架构债务 CI 门禁：禁止向 `main.py/repository.py` 增加新路由或新领域方法；
4. 建立 ADR：命名、API v2、模块边界、迁移机制；
5. 为当前变更建立可回滚 tag/commit，不在脏工作区上做大规模移动。

退出条件：Secret 权限合规；行为基线可重复；重构期间可判断行为是否变化。

### Phase 1：机械拆 Router 和 Schema（3-5 天）

按领域将路由和 Pydantic 模型移出 `main.py`，先不改变 URL、响应或业务逻辑：

1. GEO Campaign/Content；
2. Knowledge；
3. Reports/Notifications；
4. Collection/Evidence；
5. Project/Brand/Score；
6. Internal ops/phase endpoints。

退出条件：`main.py` 低于 1,000 行，最终目标低于 300 行；OpenAPI v1 diff 除 operationId 顺序外为零。

### Phase 2：拆 Application Service 和 Repository（1-2 周）

采用 Strangler 顺序逐领域迁移，不重写全部 SQL：

1. 新建明确 Repository Protocol；
2. 先迁 GEO v3，再迁 Knowledge、Report、Auth 等边界；
3. 将事务编排移到 Application Service/UoW；
4. 将外部模型和 HTTP 移到 Gateway；
5. `PostgresEvidenceRepository` 变为兼容 facade，调用新 repository；
6. 全部调用迁移后删除 facade。

退出条件：不存在超过 1,000 行的 Repository；API 不 import `scripts`、`workers` 或 adapter 私有函数。

### Phase 3：Durable GEO Generation Job（3-5 天）

1. API 创建 generation job 并冻结 Prompt/Evidence/input hash；
2. Worker 按 lease 领取，外部调用期间不持有数据库锁；
3. 结果和 Job 完成在同一事务，MinIO 使用 pending/finalize/outbox；
4. 定义 retry、regenerate、operator replay 和总模型调用预算；
5. 前端轮询 Job，支持失败重试和取消。

退出条件：API 重启、Worker OOM、租约过期和重复请求均不会丢任务或重复收费。

### Phase 4：API v2 与命名迁移（约 1 周）

1. 发布无阶段术语的 `/v2`；
2. 将 internal ops 移出产品 OpenAPI；
3. 建立 GEO 新命名和 GEO 兼容 adapter；
4. 为 v1 返回 deprecation/sunset 信息；
5. 前端全部切换 v2；
6. 兼容窗口结束后删除旧 alias。

退出条件：生产 OpenAPI 不包含 `p0a/p0b/fixture/smoke/dry-run`；非 allowlist 新代码不包含 GEO。

### Phase 5：前端、文档与遗留清理（约 1 周）

1. 拆 Admin feature；
2. 抽取共享 auth/API client；
3. 删除或归档 `apps/web` 与 `apps/dashboard-web`；
4. 重写 README、Architecture 和项目结构文档；
5. 拆分 Make/Compose；
6. 引入 CODEOWNERS 和第二维护者演练。

退出条件：默认构建只包含当前产品；新成员可仅依赖 README + docs 在 30 分钟内启动并定位主要模块。

### Phase 6：迁移与测试治理（贯穿，最终收口 3-5 天）

1. 默认 migration runner 使用 ledger/checksum；
2. 禁止修改已执行 migration；
3. 拆分两个巨型测试文件；
4. 将源码文本测试逐步改为行为/OpenAPI/AST/DB 合同测试；
5. 建立覆盖率基线并逐步提高，不在第一天设置不现实阈值；
6. 增加架构依赖测试和文件体积预算。

## 10. CI 验收门禁

整改完成需要满足以下机器可验证条件：

| 门禁 | 标准 |
| --- | --- |
| API 入口 | `app.py/main.py < 300` 行，只负责装配 |
| Router | 单文件建议 `< 600` 行，不含跨领域业务逻辑 |
| Repository | 单文件 `< 1,000` 行；不允许网络/模型调用 |
| 前端 Page | `< 300` 行；单组件建议 `< 500` 行 |
| 依赖方向 | API 不 import `scripts.*`、`workers.*`；Domain 不 import FastAPI/psycopg/httpx |
| 生产 OpenAPI | 不含 `p0a/p0b/fixture/smoke/dry-run` |
| 命名 | 非兼容 allowlist 的新增代码禁止 `GEO` |
| 文档 | 每个公共模块有职责、入口、依赖、状态机/错误合同说明 |
| 迁移 | ledger/checksum 通过；修改历史 migration 必须失败 |
| 测试 | 关键状态机、权限、跨项目、幂等、Job 恢复和浏览器路径均为行为测试 |
| Secret | 不被 Git 跟踪；文件权限不超过 `0600`；生产只用 secret file/provider |
| 遗留 | 默认构建和部署不包含退役应用 |

文件行数是警戒线而不是设计目标。不能为了通过门禁把同一 God Object 机械切成多个互相循环 import 的文件；最终验收仍以领域边界和依赖方向为准。

## 11. 实施顺序与并行边界

可以并行的工作流：

| 工作流 | 范围 | 依赖 |
| --- | --- | --- |
| A：安全与迁移机制 | Secret、Compose、migration ledger | 可立即开始 |
| B：API 机械拆分 | Router、Schema、app factory | 依赖行为/OpenAPI baseline |
| C：Repository/Application 拆分 | GEO、Knowledge、Report 等领域 | 依赖 B 的路由边界稳定 |
| D：前端 feature 拆分 | Admin/Customer/shared web | 可与 C 并行，但先冻结 API v1 |
| E：API v2/命名 | GEO 命名、兼容 adapter、internal ops | 依赖 ADR 和 B/C |
| F：文档与测试治理 | README、Architecture、行为测试 | 全程同步，最后收口 |

禁止并行修改同一个超大文件的多个 worktree；应先由 B 建立稳定模块，再按新模块分配所有权。

## 12. 风险与回滚

- 不做大爆炸改名：使用 alias、deprecation 和明确 sunset；
- 不在同一提交中同时移动代码和改变行为；
- 每个领域拆分先做 OpenAPI/行为 diff，再删除旧路径；
- 数据库只做 expand/contract，不直接 rename/drop 正在使用的对象；
- 审计事件和历史 hash 输入不改写；
- Fixture 删除前保留 CLI 等价路径；
- 遗留前端删除前确认所有入口已迁移到 Admin/Customer；
- 每个 Phase 独立可回滚，不以“全部重构完成”作为唯一可部署点。

## 14. 最终判定

当前项目不是“代码不可用”，而是“功能增长速度已经超过架构承载能力”。继续在现有 `main.py`、`repository.py`、`ProjectActions.tsx`、README 和 Makefile 上追加功能，会显著提高回归和交付风险。

建议立即暂停向这些聚合文件增加新领域功能，先完成 Phase 0 和 Phase 1。完成 Router/Schema 机械拆分和依赖门禁后，再继续开发新产品功能；否则后续每个新功能都会让真正的整改成本继续上升。
